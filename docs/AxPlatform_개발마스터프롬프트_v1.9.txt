현재 제공한 코드와 최신 변경 요청을 먼저 대조하라. 완료된 기능을 초기 샘플로 다시 만들지 말고 실제 서비스·DB·권한과 연결해 개선하라. 요청 범위의 코드·SQL·검증·전체 ZIP 납품까지 수행하라. 가능한 작업을 먼저 완료하고 결과에 영향을 주는 미확정 사항만 질문하라. 단계 명칭만 근거로 이전 단계부터 다시 시작하거나 프롬프트 정리로 코드 작업을 대신하지 마라.

보존할 v1.1 범위: 모든 기능의 대시보드, 다중 엑셀 양식·CRM, 리소스/추천 레이아웃, 실시간 갱신, 웹 데이터 편집, 추가/전체 교체 업로드, 자연어 수식의 미리보기·저장·취소를 필수 범위로 반영했다. 아래 요구와 기획안의 개정 내용을 함께 적용하라.

v1.2 중심 원칙: AI에 업무를 설명하고 지시하는 일부터 어려운 고객이 대상이다. 사용자에게 빈 채팅창을 주는 대신 업무 메뉴를 고르면 AI가 필요한 질문을 하고, 업무를 정확히 파악해 내 자료 기반 결과와 나만의 양식/CRM을 만들며 저장·추천·재사용하게 하라. 로그인/가입부터 일곱 업무에 같은 편의성 원칙을 적용한다. 기능을 무작정 추가하지 말고 기존 대표 업무의 막힘을 줄여라. 미리캔버스·Canva의 선택 대상 편집, HubSpot의 레코드 구성, monday.com의 조건 설정을 공식 자료로 참고하되 우월성을 실측한 것처럼 주장하지 마라. 구체 개정 기준은 기획안 1.4·2.1~2.2·3.2~3.10 및 각 기능의 마지막 절이다.

v1.3 엑셀 흐름(진입은 v1.9로 개정): 신규 작업은 자료 준비→편집→저장, 이미 저장된 작업은 목록→데이터 센터 원본 테이블→필요할 때 원본 편집이다. 엑셀 생성은 사진/채팅/직접 입력/Excel 가져오기 4경로다. 채팅 제안은 ‘더 이야기하기’와 ‘현재 제안으로 결정’으로 분기한다. 빈 데이터 입력용 양식과 현재 데이터 포함 다운로드를 분리하고 업로드 때 추가/전체 교체(리셋)를 고른다. 수식은 해당 엑셀 상세 대화에서 GPT가 실제 셀/계산 열에 삽입하며 적용으로 확정한다. 데이터 센터는 저장 원본 테이블을 먼저 보여 준다. 사용자가 선택할 때 조회 조건/계산 열/보고서 패널을 열고, 여러 표·그래프 보기를 저장한다. 아래 9~9-7과 기획안 7장/12.7/16.2를 동기화해 구현하라.

v1.4 확정 흐름: PPT/워드/한글/프로그램/CRM/일정에도 오버뷰와 목록, 새로 만들기, 상세 편집을 제공한다. 문서는 사진/채팅/직접 생성, 실제 글·표·도형 삽입과 직접/AI 수정, 버전별 저장/출력을 구현한다. 프로그램은 요청 기능을 부품 목록으로 관리하고 추가/삭제/수정 후 변경사항 저장 시 V2 등 새 버전과 다운로드 가능한 실행 패키지를 만든다. CRM의 구조/고객/보기, 일정/반복/알림의 변경 범위를 분리한다. 3.11·6.7·8~11장·12.8·15.4·16.3을 반영하며 기존 v1.3 엑셀 요구를 축소하지 마라.

v1.5 UX 보강: 순차 진행 중 질문 과다를 막고 초안을 먼저 확인하게 하라. 선택 대상에서 정밀 설정으로 이동하고, 모호한 요청은 실제 작은 미리보기로 비교하며, 변경 범위·조건 시험·오류 위치·양식 재사용·작업 재개를 명세하라. 기획안 3.12~3.17, 4.8, 7.13, 8.11, 9.8, 10.12, 11.9, 12.9, 15.5, 16.4를 함께 적용하라. 기존 v1.4까지의 확정 기능은 유지한다. 새 기능 수를 늘리는 것으로 사용성 개선을 대체하지 마라.

v1.6.1 관리자·동적 권한 확정 요구: 로컬·서버(운영 포함) 모두 최초 초기화하는 관리계정 admin/12345와 PasswordEncoder 해시 저장, 로그인창의 관리자로그인, 성공 후 관리자페이지 이동, 회원관리와 권한관리를 구현하라. 게스트/1단계/2단계/3단계에 업무 그룹 전체 또는 세부 행동을 드래그앤드롭으로 배정하며 기능 카탈로그의 추가/조회/수정/삭제를 제공하라. 기존 무료/베이직/프로/맥스와의 기본 대응, 관리자 별도 역할, 서버의 행동별 검사와 정책 변경 반영은 기획안 4.9~4.10·5.6~5.7·12.10·14.4~14.10·15.6·16.5를 따르라. 기존 보존 정책을 세부 권한 우회의 근거로 사용하지 마라.

v1.6.2 화면 기술 확정: Spring Boot + Spring MVC + Thymeleaf가 화면 렌더링을 담당한다. JavaScript·CSS 및 필요한 라이브러리로 동적인 사용 경험을 구현한다. 실제 React/TypeScript/Vite 프런트엔드 요구는 폐기하며 Thymeleaf를 빈 React 셸로 사용하지 않는다. 단일 Maven 구조·비동기 갱신·일반 JS 연동·실행 절차·검수는 기획안 3.4·12.1~12.2·12.11·15.2·16.6을 따른다. 모든 기존 업무와 로컬·서버 admin/12345 초기화 및 PasswordEncoder 규칙은 유지한다.

1. 프로젝트 목표

- 프로젝트명: AxPlatform. 표기 이름은 설정으로 바꿀 수 있게 한다.
- 슬로건 원안: ‘최소 3명의 인건비를 절약해 드립니다.’ / ‘나만의 비서를 만들어 보자.’
- 첫 번째 슬로건은 검증할 사업 목표이며 모든 고객에게 실제 절감을 보장하는 성능 조건으로 임의 확정하지 않는다. 공개 문구는 검증한 근거와 함께 결정한다.
- 대상: AI에게 어떤 말을 해야 하는지 모르는 소규모 제조업·도소매·현장 서비스·사무 담당자.
- 고객이 메뉴만 골라도 시작할 수 있어야 한다. AI가 선택지와 예시로 목적·업무·자료·원하는 결과를 파악하고, 이해한 내용을 확인한 뒤 제안·미리보기·수정·내 양식 저장·추천·재사용을 돕는다. Claude/Gemini/ChatGPT 자체의 기능 결여를 주장하지 않고 이 고객의 시작과 반복 업무에 집중한다.
- 핵심 기능 7개: 간단한 프로그램 만들기 / 엑셀 관리·누적 데이터·분석 / 워드 / 한글(HWP) / PPT / 나만의 CRM / 거래처 연동 일정.
- 지향점은 파일을 한 번 만들어 주는 서비스에 그치지 않고 자료·양식·거래처·일정을 연결해 반복 업무를 줄이는 것이다.

2. 개발 환경과 결정 방식

- Java 17, Maven, Spring Boot, Eclipse에서 import 가능한 프로젝트, Ubuntu 배포를 기본 조건으로 한다.
- 프런트엔드는 Spring Boot + Spring MVC + Thymeleaf로 렌더링하는 화면으로 확정한다. JavaScript·CSS와 필요한 라이브러리로 순차 질문·부분 갱신·정밀 편집·애니메이션을 구현하라. ‘React처럼’은 동적인 느낌만 뜻하며 React·TypeScript·Vite 앱을 만들거나 이를 다시 선택 사항으로 묻지 마라.
- DB는 MariaDB를 권장 기본으로 시작한다. PostgreSQL이 유리한 구체적 이유가 있으면 비교 후 P0에 결정하되 이유 없이 복수 DB를 도입하지 않는다.
- 착수 시점에 지원 중인 Java 17 호환 Spring Boot 및 SDK/라이브러리 버전을 공식 문서로 확인하고 고정한다. 버전이 익숙하다는 이유만으로 지원 상태를 단정하지 않는다.
- 모듈로 나눈 단일 Spring Boot 애플리케이션과 별도 긴 작업 worker를 기본으로 한다. 필요성이 검증되지 않은 다수 마이크로서비스·Kubernetes를 먼저 도입하지 않는다.
- 공식 자료로 확인한 사실, 내가 확정한 요구사항, 네 권장안, 아직 결정하지 않은 항목을 구분한다.
- 사용자 지시를 우선하고, 사소한 구현 선택은 근거를 기록하며 진행한다. 비용·데이터 구조·서비스 범위를 크게 바꾸는 선택은 구현 전에 확인한다.
- 확인하지 못한 API 필드·응답 코드·콘솔 메뉴·라이선스·실행 결과를 추측해서 확정하지 않는다.

2-1. Thymeleaf와 JavaScript의 확정 구현 계약

- Spring MVC Controller에서 Thymeleaf 최초 화면과 모델을 렌더링하라. 공통 레이아웃·메뉴·폼·팝업은 fragment로 재사용하고 업무별 JS 모듈을 연결하라.
- 페이지 GET, HTML fragment 조회, JSON 조회/변경 API의 경로·응답을 구분하라. 서비스·권한·검증은 공유하라. 단순 폼/목록 부분 갱신은 fragment, 그리드/차트/달력 데이터 갱신은 JSON을 기본으로 하며 같은 영역의 상태를 이중 관리하지 마라.
- fetch 공통 요청 모듈과 화면별 JavaScript·CSS를 기본으로 하라. 필요한 일반 JS 라이브러리는 적극 활용하되 실제 기능·상업적 라이선스·접근성·한글 입력·성능을 검증하라. React 전용 컴포넌트 도입을 위해 플랫폼 스택을 바꾸지 마라.
- 질문 전개·팝업·탭·드래그·편집·AI 대화·실시간 갱신마다 전체 화면을 다시 로딩하지 마라. 편집기의 DOM/초안은 해당 JS API로 관리하고 HTML 교체로 입력을 소실시키지 마라. 교체 전 이벤트/타이머/연결/인스턴스를 정리하고 중복 초기화를 방지하라.
- 서버 확정 상태와 편집 초안을 구분하고 선택·초점·스크롤·저장/취소 상태를 보존하라. 요청 순서·중복 클릭·늦은 AI 응답·버전 충돌을 처리하라. 페이지의 직접 링크·새로고침·뒤로가기와 query/history 복원이 일치해야 한다.
- 같은 출처의 세션 인증을 기본으로 하라. 폼과 fetch의 변경 요청에 CSRF 토큰을 적용하고 로그인/로그아웃 후 토큰 정책을 검수하라. 인증 만료/권한 부족 응답을 구분하고 로그인 HTML을 JSON이나 편집 영역으로 삽입하지 마라. 페이지·fragment·API·서비스 모두 서버 권한을 검사하라.
- 출력은 기본 이스케이프하고 AI/사용자 HTML을 무검증 삽입하지 마라. 서버 키/토큰을 Thymeleaf 모델·렌더링 HTML·JS 인라인·data 속성·정적 JS로 내려보내지 마라. 문서 엔진은 검증된 JS SDK/임베딩·서버 저장 어댑터로 연결하라.
- 루트 pom.xml의 단일 Maven 프로젝트에 templates, static/css·js·vendor 및 업무 소스를 포함하라. 기본 Eclipse 실행과 Ubuntu JAR 실행에 별도 frontend 서버·Node/npm을 요구하지 마라. 필요한 외부 엔진은 별도 준비 조건을 안내하라.
- 브라우저 라이브러리는 고정 버전·라이선스·원본/배포본·사용처를 기록하고 배포 가능한 자원을 ZIP에 포함하라. CDN 연결에만 의존하지 마라. 선택적 자원 가공 도구는 목적·재현 절차·결과물을 제공하라.
- Thymeleaf 채택을 이유로 실제 그리드·문서 객체 편집·CRM·달력·부품/V2·관리자 드래그 권한을 축소하지 마라. 기획안 16.6 UI-TECH-01~05를 P1 기반과 P2~P6 실제 업무에서 검수하라.

3. 반드시 지킬 UX

- 공통 흐름: 업무 메뉴/예시→내 양식 추천 또는 새로 만들기→목적/자료/결과를 좁히는 질문→‘이렇게 이해했어요’ 확인→내 자료 미리보기→선택 부분 정밀 조정→저장/출력→다음 업무에서 재사용.
- 질문과 자료 제공 순서는 업무에 맞게 조절한다. 자료가 있으면 읽어 중복 질문을 줄이고 자료가 없으면 선택형 질문으로 시작한다. 업로드나 긴 자유 입력을 무조건 필수로 하지 않는다.
- 한 번에 한 결정 주제를 보여준다. 쉬운 선택지 2~4개·짧은 예시·추천 이유·‘잘 모르겠어요’·‘직접 입력’을 권장하되 불필요한 선택지를 채우지 않는다.
- 대표 첫 작업은 핵심 질문 3~5개로 유용한 초안을 만드는 것을 목표로 한다. 고정 문항 수를 채우지 말고 모호함이 남으면 필요한 질문을 추가한다. 금액 단위·리셋 대상·수신자·실행 환경 같은 조건을 편의성 때문에 추측 확정하지 않는다.
- 확인됨/자료에서 확인/AI 추정/미확인/충돌을 구분한다. 이미 확인한 것은 생략하고 중요한 모호함부터 질문한다. 목표가 바뀌면 관련 제안만 재검토하고 기존 자료·관계없는 답은 유지한다.
- 업무 요약에 목적·대상·자료·원하는 결과·반복 방식·미확인 조건을 카드로 표시하고 각 카드를 수정할 수 있게 한다. 확인한 요약과 저장 결과가 일치해야 한다.
- 처음에는 추천, 대상을 고르면 빠른 조정, ‘자세히 조정’에서 정확한 값/조건을 보여준다. 초급/전문가 프로그램을 분리하거나 모든 설정을 처음부터 나열하지 않는다.
- 완료 질문은 짧은 요약으로 접고 다음 필요한 요소가 같은 작업 공간에 자연스럽게 나타난다. 진행 위치와 이전 답 수정은 항상 찾을 수 있게 한다.
- 관련 항목 펼침/접힘에 150~250ms 전환을 권장한다. 예상 못한 화면 이동/외부 실행, 입력 중 강제 스크롤, 모달 중첩, 기다려야 조작 가능한 장식 효과는 피한다.
- 키보드 대체 조작, 드래그 대체 버튼, 포커스 복귀, 모션 감소, 터치/반응형을 구현한다. 단순 로그인까지 인위적으로 여러 단계로 쪼개지 않는다.
- ‘이대로 진행’·‘다른 제안 보기’·‘직접 수정’을 일관되게 사용한다. 다른 제안은 기존안을 보존한다. 선택 대상의 정확한 속성은 직접 편집으로도 조정한다.
- 반복 작업은 지난 양식으로 추가/자료만 교체/기존 설정 수정으로 바로 시작한다. 최초 질문을 매번 반복하지 않는다.
- 업무 답·자료·초안을 새로고침/뒤로가기/재접속에 복구한다. 비밀번호·OTP·복구 토큰·외부 비밀값은 AI나 복구용 브라우저 저장소에 남기지 않는다.
- 모델 장애는 기본 질문으로 이어가고 기존 데이터 조회/직접 편집/다운로드를 차단하지 않는다. 빈 상태·로딩·실패·미연동·권한/한도·저장 실패를 실제 동작으로 구현한다.
- UI의 간격/입력/버튼/표를 공통 토큰으로 통일하고 알 수 없는 진행률을 꾸며내지 않는다.

3-1. 기능별 대시보드와 탐색
- 일곱 기능 모두 대시보드+요약+내 작업 목록을 제공한다. 플랫폼 홈→기능 오버뷰→개별 항목 대시보드/상세→편집·실행으로 연결한다.
- 프로그램: 만든 앱 수/상태/최근 활동과 목록, 개별 실행/편집/버전/기록. 수집한 실제 실행 이벤트만 집계한다.
- 워드·한글·PPT 각각: 문서 수/상태/최근 작업/리소스 요약, 검색·필터·정렬·카드/리스트와 미리보기.
- 엑셀: 전체 오버뷰/목록→저장 데이터 센터의 원본 테이블이 기본. 미저장 작업은 작성 단계로 이어간다. 원본 편집/계산 열/보고서/다운로드는 해당 행동을 선택하면 펼친다.
- CRM: 여러 CRM 오버뷰→선택 CRM의 고객 현황·목록·설정. 일정도 오늘/이번 주/기한 경과/충돌 대시보드와 달력/목록을 제공한다.
- 사업·기간·범위와 지표 단위, 최근 갱신을 표시하고 클릭 시 해당 근거 데이터로 이동한다. 서로 다른 의미의 금액/단위를 임의 합산하지 않는다.
- 핵심 요약·할 일·최근 항목부터 보여주고 위젯 선택/숨김/순서·즐겨찾기·저장한 보기를 지원한다. 모든 통계를 나열하지 않는다.
- 탐색 왕복 시 검색·필터·정렬·스크롤을 복원한다. 빈 상태는 실제 생성 버튼을 제공하고 성과를 꾸며내지 않는다.

3-2. 실시간과 확정 데이터
- 실시간은 서버 확정 데이터가 자동 반영되는 의미다. 미저장 초안·PC의 외부 Excel 파일 변경까지 자동 반영한다고 표현하지 않는다.
- 연결 중/최신/갱신 중/지연/끊김과 마지막 갱신 시각을 표시한다. 단순 집계는 확정 후 5초 이내 목표로 시험하고 연결 실패 시 30초 재조회+수동 갱신을 권장한다. 수치는 검증 전 목표다.
- 대량 import/수식 재계산은 작업 상태·집계 버전을 표시하고 서로 다른 데이터 버전의 숫자를 섞지 않는다.
- 확정 변경 이벤트는 범위·객체·버전·이벤트 ID로 전달하고 중복/역순/유실/재접속을 처리한다. SSE/WebSocket 방식은 구현 요구에 맞게 선택한다.
- 편집 중인 화면을 새 이벤트가 강제로 덮어쓰지 않는다. 저장 충돌을 보여주고 재연결 시 스냅샷을 다시 받아 누락을 복구한다.
- 대시보드 조회/갱신은 검증된 집계 API로 처리하며 매번 AI 호출/크레딧 차감하지 않는다.

3-3. 선택 대상과 정밀 조정의 공통 계약
- 문서>슬라이드>표>열처럼 현재 대상을 표시하고 관련 속성만 보여준다. 숫자/단위 입력과 드래그를 함께 지원한다. 설정 검색/‘이 항목 설정’ 진입으로 접힌 옵션도 찾을 수 있게 한다.
- 직접 조작과 AI 제안은 같은 필드/속성·명령·초안에 반영한다. ‘이 표만’ 요청에 다른 슬라이드/고객/데이터를 바꾸지 않는다. 편집 잠금은 AI에도 적용하되 접근 권한과 구분한다.
- 다중 선택은 공통 속성만 조정하며 값이 다른 경우 ‘여러 값’으로 표시한다. 미지원/권한 제한은 이유를 설명하고 실제 되는 것처럼 보이지 않는다.
- 미리보기 반영은 초안 변경, 변경사항 저장은 표시된 초안의 확정이다. 이번 AI 제안 취소는 해당 변경 집합만 제거하고 기존 수동 초안은 유지한다. 전체 변경 취소는 마지막 확정 버전으로 돌아가는 별도 행동이다.
- 선택 범위/현재 문서 전체/내 기본 양식 저장을 구분한다. 기본 적용은 선택 범위이며 확장할 때 표시한다. 직접 값과 상속 기본값을 구분하고 선택 속성만 기본값 복원한다.
- 작은 외형 변경은 즉시 초안 반영+실행 취소로 처리한다. 데이터 리셋/외부 발송/결제 등 기존 중요한 확인 단계는 유지한다.
- 조건에 따라 숨긴 초안은 보존하되 비활성 값을 신규 실행/필수 검사에 몰래 쓰지 않는다. 기존 확정 데이터는 숨김 때문에 삭제하지 않는다. 조건과 접근 권한을 혼동하지 않는다.

3-4. 일곱 메뉴별 질문의 출발점
- 프로그램: 줄일 업무→기기/온라인 또는 오프라인→사용자→입력과 결과. 프레임워크/언어/DB를 고객에게 고르게 하지 않는다.
- 엑셀: 생성 방식 선택 후 사진은 분석/검수, 채팅은 질문/헤더 제안/결정, 직접 입력은 빈 그리드로 시작한다. 생성 이후 수식과 분석을 상세에서 설정하며 세 흐름을 동일한 질문 마법사로 강제하지 않는다.
- 워드: 목적→독자→내용/자료→분량·말투. 한글: 제출 목적→지정 서식→자료→필수 형식.
- PPT: 발표 목적/청중→핵심 메시지→자료→발표 시간/분량. 개요를 확인한 후 레이아웃을 추천한다.
- CRM: 관리 대상→놓치기 쉬운 업무→기존 목록→후속 행동. 예: 납품 거래처/재주문 연락이면 관련 항목과 보기 추천.
- 일정: 할 일→거래처/개인→일시→필요할 때 반복/알림. 시작 화면의 날짜·고객은 다시 묻지 않는다.
- 위 순서는 업무별 기준이며 자료/선택 양식에 답이 있으면 생략한다. 목적 변경/모호한 답/자료 없음/모델 실패의 분기를 설계한다.

3-추가. 모든 기능의 탐색과 저장
- 오버뷰와 목록을 구분한 화면/탭, 명확한 신규 생성 버튼, 목록에서 실제 편집 가능한 상세 진입을 제공한다. 버전 목록은 해당 항목 상세 안에 두고 V1/V2를 별개 프로젝트로 중복 집계하지 않는다.
- 문서는 편집기, 프로그램은 부품/미리보기, CRM은 고객 목록을 기본 상세로 열고 개별 현황을 별도 탭으로 둔다. 일정 목록/달력은 같은 일정 상세로 연결한다.
- 생성은 필요한 방식만 선택한 뒤 순차 진행한다. 직접 작성은 AI 없이 시작한다. 채팅 제안의 더 이야기하기/현재 제안으로 결정은 대화 지속/선택 제안 초안 생성이며 최종 저장·활성화·발송이 아니다.
- 자동 보관은 초안 상태다. 확정 저장·파일 생성·프로그램 활성화를 분리한다. 다운로드 시 미저장 변경이 있으면 저장 후 다운로드와 마지막 저장본 다운로드를 구분한다.
- 문서/프로그램은 불변 버전, CRM 고객/일정은 레코드 이력, CRM 구조는 스키마 버전, 보기는 표시/집계 정의다. 전부 같은 V2 복제로 구현하지 않는다.
- 선택 요소의 속성/AI 패널만 나타나게 하고 자세한 설정은 필요할 때 확장한다. 취소는 이번 제안/전체 초안으로 구분하고 저장 실패에서도 초안을 보존한다.

3-5. 짧은 안내와 결과 중심의 정밀 편집
- 한 가지 결정에 필요한 항목을 함께 보여라. 이미 제공한 답·자료는 확인 상태를 표시하고 다시 묻지 마라. 최소 정보가 모이면 ‘현재 정보로 초안 보기’를 제공하되 미확인 사실은 명시하고 금액/수신자/리셋 등 중요 조건은 실제 반영 전에 확인하라. 엑셀의 ‘더 이야기하기’와 ‘현재 제안으로 결정’을 유지하라.
- 업무 예시로 시작하면 해당 메뉴와 맥락을 연결하라. 자료 확인/초안/다듬기/저장의 안정된 단계를 표시하고 질문 수가 변하는 동안 임의 진행률을 만들지 마라. 답 수정은 관련 질문/제안만 다시 검토하라. 첫 작업과 무관한 프로필·연동을 먼저 요구하지 마라.
- 결과의 표/문단/도형/열/CRM 항목을 선택하면 같은 대상의 속성과 AI 수정이 열리게 하라. 대상 위치, 적용 범위, 초안 revision을 공유하라. 쉬운 말로 설정을 검색해 실제 속성으로 이동하게 하고 추천값/드래그/직접 숫자가 같은 값에 반영되게 하라. 단위와 허용 범위, 양식 기본값/직접 변경 여부를 확인하고 선택 속성만 초기화할 수 있어야 한다.
- ‘더 깔끔하게’ 같은 모호한 요청은 필요한 경우 사용자 자료를 유지한 2~3개 부분 미리보기로 비교하라. 매번 추가 선택을 강요하지 마라. AI 응답은 이해/변경/미리보기/행동을 짧게 먼저 보여주고 근거는 펼쳐 보게 하라.
- 조건/필터/수식을 읽을 수 있는 구조로 표시하고 일치·불일치·빈 값 사례를 실제 엔진으로 시험하게 하라. AND/OR 그룹과 기준 날짜/단위를 편집할 수 있어야 한다. 조건 시험은 운영 데이터 변경이나 외부 발송을 실행하지 마라.

3-6. 저장 범위와 회복 가능한 흐름
- ‘이번 변경 N개’에서 내용/구조/보기/양식 변경을 확인하게 하라. 단순 편집마다 확인창을 띄우지 말고 데이터 파괴·외부 실행·범위 확대에서 확인하라. AI 취소는 이전 직접 편집을 보존하고 의존 변경은 함께 검증 가능한 묶음으로만 반영하라.
- 오류는 셀/객체/필드 ID, 수정 이유/방법, 차단 수준과 연결하라. 여러 오류는 다음 오류로 이동하며 이미 해결한 입력을 보존하라. 미확인 OCR은 원본 대조로 검수하고 일괄 수정은 대상과 샘플을 먼저 보여라.
- ‘이어서 수정’, ‘이 설정으로 새로 만들기’, ‘내 양식 업데이트’를 분리하라. 기본 양식의 재사용에 실제 고객 데이터·수신자·비밀정보를 포함하지 마라. 보기 필터/열 숨기기는 데이터 삭제가 아니다. 작업/양식별 선호를 사용자 확인 없이 모든 사업의 영구 기본값으로 확장하지 마라.
- 비동기 작업의 실제 상태와 재개 위치를 제공하라. 취소 요청/완료, 부분 결과/전체 완료, 서버 저장/미반영 입력을 구별하고 재시도 멱등성 및 늦은 AI 결과 충돌을 처리하라. 목록 갱신이 입력 초점과 선택을 빼앗지 않게 하며 최신 여부를 표시하라.
- 모바일에서는 사진 검수·고객 메모·일정과 동일 레코드의 행 입력을 우선 지원하라. 큰 화면이 필요한 정밀 편집은 지원 범위와 이어 하기 경로를 안내하라. 한글 IME 중 Enter 조기 확정/전송, 키보드 초점 손실, 애니메이션 축소 시 흐름 상실을 검수하라.

3-7. 기능별 실제 적용
- 인증: 남은 필수 정보와 이유를 표시하고 제공자 확보값을 재활용하라. 연락처/이메일 필수, 계정 분리, 인증 보안은 유지하라. 자동완성·OTP 붙여넣기를 지원하고 완료 후 하던 업무로 복귀하라.
- 엑셀: 월급×복무기간의 기간 단위/일할 계산을 확인하고 대표 행 결과를 제시한 뒤 수식 넣기/적용하라. 반복 업로드는 기존 매핑을 추천하되 추가/리셋은 사용자가 결정한다. 차트에서 근거 행으로 돌아갈 수 있게 하라.
- 문서: 선택 객체의 정확한 수치 조정과 부분 대안 비교, 고정 레이아웃/바뀔 내용의 양식 구분, 출력 넘침/누락 위치 안내를 구현하라. 사진의 배경 사용과 편집 가능한 내용 추출을 구별하라.
- 프로그램: 부품을 업무 행동으로 이름 짓고 시험 데이터를 사용하라. 부품 제거와 데이터 삭제를 구분하라. V2 저장/빌드/다운로드/활성화 상태를 분리하고 실패 부품의 수정 위치를 연결하라.
- CRM: 통합/개별 CRM과 사업 대상을 표시하라. 열 표시와 필드 정의, 보기와 고객 데이터를 분리하라. 조건부 필드는 실제 예로 시험하고 발송 전 대상/내용/비용을 확인하라.
- 일정: 기존 거래처 선택과 신규 최소 등록, 일정 메모와 거래처 공통 메모, 반복 범위와 알림 변경을 구별하라. 필터로 숨겨진 일정은 날짜 이동/조건 해제로 찾게 하라.

4. 계정 식별 정책 — 반드시 보존

- EMAIL / GOOGLE / KAKAO / NAVER를 제공한다.
- 같은 이메일이어도 EMAIL 계정과 각 SNS 계정은 별도 계정이다. 자동 연결·자동 병합하지 않는다.
- 내부 account_id로 회원을 식별한다. EMAIL은 정규화된 로그인 이메일에 유일 제약, SNS는 제공자+제공자 고유 ID에 유일 제약을 둔다.
- Google은 sub, 카카오·네이버는 공식 프로필 고유 ID를 사용한다. SNS 프로필 이메일로 같은 계정 여부를 판정하지 않는다.
- account.email 전체에 전역 unique를 두지 않는다. 동일 연락처를 여러 별도 계정이 사용하는 것은 허용한다.
- 별도 계정끼리 데이터·구독·혜택을 임의 공유하지 않는다. 계정 병합은 1차 범위에서 제공하지 않는다.
- 인증 권장안은 Spring Security OAuth2/OIDC와 자체 이메일 인증이다. Firebase를 채택할 경우 카카오·네이버·동일 이메일 분리 요구를 충족하는 구체 설계를 먼저 제시하고 인증 기준이 중복되지 않게 한다.

5. SNS 가입·로그인

- ‘SNS 로그인’으로 인증 성공: 기존 계정이면 로그인, 신규면 필수 정보·서비스 약관·검증을 완료하고 자동 가입·로그인한다.
- ‘SNS 회원가입’으로 인증 성공: 신규면 가입·로그인, 이미 같은 제공자 ID가 있으면 중복 안내와 ‘로그인으로 계속’ 버튼을 제공한다. 추가 계정을 만들지 않는다.
- 동의 화면은 제공자 정책과 기존 동의 상태에 따라 표시될 수 있다. 매번 새 동의 화면이 나온다고 전제하지 않는다.
- 서비스 약관 동의는 제공자 정보 제공 동의와 별도로 기록한다.
- 모든 가입은 이메일·연락처가 필수다. SNS에서 받지 못하거나 검증 상태가 불분명하면 보완 입력·검증을 받는다.
- Google 기본 로그인에서 전화번호를 받을 수 있다고 가정하지 않는다. 카카오·네이버의 동의항목·앱 승인·누락값을 처리한다.
- 권장안: 제공된 번호를 미리 채우고 모든 가입에서 SMS OTP로 수신 가능한 번호인지 확인한다. 이것을 실명/명의 본인확인이라고 표현하지 않는다.
- 검증된 이메일 클레임은 사용할 수 있고, 미검증·보완·변경 이메일은 이메일 인증한다.
- 필수 정보가 완성되기 전에는 가입 대기 상태로 유지하며 일반 업무 API 접근을 금지한다.
- 정지·탈퇴 처리 중·동의 취소·콜백 재호출·중복 클릭을 처리한다.
- OAuth state 및 지원되는 PKCE, OIDC nonce·서명·issuer·audience·만료 검증, 세션 교체, 허용된 리다이렉트만 사용한다.

6. 이메일 회원가입·아이디 찾기·비밀번호 재설정

- 이메일 회원가입 필수: 이메일, 비밀번호, 비밀번호 확인, 이름, 연락처, 필수 약관.
- 이메일로 코드를 보내 5분 안에 인증해야 한다. 이메일/연락처 변경 시 이전 인증을 재사용하지 않는다.
- 권장 초기값: 6자리 난수 OTP, 60초 재발송 제한, 코드당 5회 실패 후 폐기. IP·대상·세션별 제한도 둔다.
- 목적·대상·임시 세션·만료·시도횟수·단일 사용을 서버에서 관리한다. 재발송은 이전 코드를 폐기한다. 짧은 코드를 단순 해시만 하지 말고 서버 비밀키를 이용한 검증값으로 저장한다.
- 인증 증표 소비와 회원 생성은 동시 요청에서도 한 번만 완료되도록 처리한다.
- 비밀번호는 검증된 PasswordEncoder로 해시하고 원문을 저장·로그 출력하지 않는다.
- 가입 성공 후 자동 로그인한다.
- 아이디 찾기: 연락처 입력 → 연결된 EMAIL 로그인 이메일을 등록된 번호로 SMS 전송. SNS 계정은 제외하고 화면에는 가입 여부·이메일을 노출하지 않는다. 발송 남용 제한을 둔다.
- 비밀번호 찾기: 이메일+연락처 일치하는 EMAIL 계정에만 이메일 재설정 링크 발송. 화면 응답은 일치 여부와 관계없이 동일하게 한다.
- 링크는 충분히 긴 난수·서버 해시 저장·단일 사용·권장 15분 만료로 구현한다. 링크 GET으로 토큰을 소비하지 않는다.
- 새 비밀번호 적용 시 토큰을 소비하고 기존 세션을 무효화한다. 자동 로그인하지 않고 로그인 화면으로 이동한다.
- 복구 링크는 설정한 공개 base URL로 생성하며 Host 헤더에 의존하지 않는다. 코드·토큰은 로그/분석 도구/외부 리퍼러에 남기지 않는다.

6-1. 로그인·가입도 편하게 쓰는 화면으로 구현
- 인증은 검증된 고정 흐름과 전용 입력창이다. AI가 비밀번호/OTP를 받거나 로그인 성공/동의/중복 여부를 판정하지 않는다.
- 로그인/가입 및 Google/Kakao/Naver/이메일 방식은 찾기 쉽게 보여주고 선택 방식의 상세 입력만 연다. 이메일 로그인은 이메일+비밀번호 한 묶음, 자동완성/비밀번호 관리자 지원.
- 이메일 가입은 이메일 확인→기본정보/연락처 확인→약관/완료의 논리적 단계로 구성한다. 비밀번호와 확인은 함께 둔다. 가입에 업종 설문/회사 규모 질문을 끼워 넣지 않는다.
- SNS는 받은 유효 정보를 활용하고 누락/검증 필요한 항목만 보완한다. 제공자별 계정 분리 정책을 짧게 안내하고 공개 이메일 조회로 가입 방식을 노출하지 않는다.
- OTP는 붙여넣기/자동완성/남은 시간/재발송/번호 수정/만료 안내를 지원한다. 인증 상태는 서버 기준, 만료 시 일반 입력까지 전부 삭제하지 않는다.
- 복구는 선택 목적의 입력만 보여주며 기존 익명 응답/만료/단일 사용/자동 로그인 금지 정책을 유지한다.
- 가입 후 무료 팝업을 닫거나 무료로 시작하면 업무 선택으로 바로 이어진다. 도움말·온보딩·요금제 팝업을 중첩하지 않는다.

6-2. 초기 관리자와 로그인 경계
- 로컬과 서버(운영 프로필 포함)의 DB별 최초 초기화에서 SYSTEM_ADMIN/SUPER_ADMIN 유형의 admin/12345 계정을 정확히 1개 생성하라. PasswordEncoder.encode("12345")로 생성한 해시만 DB에 저장하고 인증은 PasswordEncoder.matches로 검증하라. 이중 인코딩/평문 저장·비교를 금지한다. 같은 DB를 공유하는 서버/로컬은 같은 계정을 사용한다. 재시작·재배포·프로필 변경 시 기존 암호/권한/상태를 덮어쓰지 마라. 초기화 기록·트랜잭션·고유 제약으로 동시 중복을 막고 충돌 계정을 임의 승격하지 마라. 계정 소실 후 기본 암호 자동 재생성도 금지한다.
- 로그인창에 관리자로그인 메뉴를 제공하라. 권장 /admin/login에서 ID/암호 인증 후 /admin으로 이동하라. 관리자 홈에는 회원관리와 권한관리 메뉴가 있어야 한다. 로컬·서버 모두 초기 계정으로 로그인하면 관리자 홈으로 이동하고 암호 변경 진입점을 제공하라. 운영 프로필이라는 이유로 초기 생성/기본 암호 로그인을 차단하지 마라. README_LOCAL과 README_UBUNTU에 초기 값·생성 시점·해시 저장·경로·변경·재배포 보존·복구 절차를 안내하라.
- 일반 EMAIL/SNS 계정과 관리 자격증명을 분리하라. 문자열 admin만으로 권한을 주지 말고 계정 유형/역할/상태를 검증하라. 관리자 공개 가입을 만들지 마라. 시드 관리계정은 일반 고객 가입이 아니므로 가짜 이메일/번호/검증값을 넣지 마라. 고객 회원가입의 이메일/연락처 필수는 유지한다.
- /admin 및 /api/admin/**는 서버에서 관리 역할을 검사하라. 일반 등급에 관리 전용 권한을 배정하지 마라. 마지막 활성 최고관리자 삭제/정지/강등을 막고 일반 복구/무료 팝업에서 관리계정을 제외하라. 세션 교체·실패 제한·CSRF 등 기존 검증도 적용하라.
- 관리자는 모든 구현된 업무 기능을 상품 제한 없이 사용하며 관리자 소유 시험 워크스페이스의 업무 화면으로 이동할 수 있어야 한다. 다른 고객 자료 자동 접근, 미구현/미연동 성공 처리, 무제한 외부 비용 실행으로 해석하지 마라. 지원 접근은 대상·사유·감사 이력을 별도로 남겨라.

7. 요금제와 첫 로그인 팝업

- 상품은 FREE/BASIC/PRO/MAX, 표시명 무료/베이직/프로/맥스를 유지한다. 기본 권한 등급은 게스트/1단계/2단계/3단계로 각각 대응한다. 게스트는 가입한 무료회원이며 비로그인 ANONYMOUS와 다르다. 관리자 역할은 상품 등급과 분리한다.
- 가격·숫자 한도는 미정이다. 아래 기능 배분은 초기 권장 정책이며 저장된 등급별 세부 권한으로 변경할 수 있어야 한다. 실행 시 등급 자동 상속을 하거나 플랜명을 비교해 고정 허용하지 마라.
- 무료: 제한된 엑셀·문서 실제 생성/다운로드 체험, 개인 기본 일정.
- 베이직: 누적 엑셀·양식 재사용·기본 분석, 워드/한글/PPT 정식 제작, 거래처 주소록 연동 일정.
- 프로: 베이직+맞춤 CRM·고급 분석·Gmail/문자/알림톡 연결·기본 자동화.
- 맥스: 프로+검증된 구성요소의 프로그램 생성·확장 자동화·높은 처리량/동시 작업 한도.
- 미구현 기능은 유료 권한과 별도로 출시 예정으로 표시한다. 실제 HWP 엔진 미확보 시 한글 기능 완료로 판매하지 않는다.
- 기능 코드/한도 기반 서버 권한 검사로 구현하고 플랜 이름 if문을 여러 위치에 복제하지 않는다.
- 첫 무료 로그인에 요금제 설명 팝업을 표시한다. 닫기/무료로 시작/요금제 보기/7일간 안 보기 제공.
- 숨김 만료시각은 서버 저장, 기기 간 유지, 로그인 세션당 최대 1회, 메뉴 이동·새로고침 재노출 금지, 유료에는 미노출.
- 플랜은 권장 기본으로 워크스페이스 단위다. 초기 계정에는 소유자 1명인 워크스페이스 하나를 만든다. 팀 좌석 판매는 별도 후속 범위다.
- 사용량은 실행 전 원자적 예약 → 성공/실패/취소에 따른 정산·반환. 고객 차감량과 실제 공급자 비용을 분리한다.
- 청구주기/갱신/해지예약/만료/실패/유예/환불/다운그레이드를 모델링한다. 클라이언트의 결제 성공 화면만 믿지 않는다.
- PG 후보는 토스페이먼츠 자동결제다. 계약/테스트/운영 키·빌링키·주기적 청구 작업·웹훅 검증·대사를 확인한다.
- 중복 청구와 중복 웹훅을 멱등하게 처리하고 순서 뒤집힘·누락을 복구한다.
- 만료 후 신규 유료 작업/자동화는 제한하고 기존 자료를 보존한다. 기본 만료 정책에 조회/내보내기/삭제를 명시 배정할 수 있지만 관리자가 철회한 행동은 차단한다. 보존을 권한 우회로 사용하거나 자료를 임의 즉시 삭제하지 마라.

7-1. 동적 세부 권한의 판정
- 네 등급의 권한 집합은 독립이며 복사는 현재 값 복사다. 최초 정책만 상위 플랜이 하위 기능을 포함하도록 구성한다. 상품/유효 등급/출처를 표시하고 수동 등급은 워크스페이스·사유·적용/선택 만료 시점을 기록하라. 수동 지정이 유효하면 결제 웹훅이 덮어쓰지 않고 해제 시 현재 구독 등급으로 복귀한다. 권한 부여로 결제 성공을 만들지 마라.
- 정상 인증/계정→자료 범위→기능 구현/활성→등급 행동 권한→의존 권한→한도/연결/업무 검증으로 검사하라. 기본은 거부이며 관리자도 자료 범위와 검증을 우회하지 않는다. 상품 기능 허용과 사용량 한도는 별도다.
- FeatureGroup/PermissionDefinition/Dependency/AccessTier/PolicyVersion/Grant/WorkspaceTierOverride/Audit 구조를 기존 Entitlement와 통합하라. 코드 불변, 정책/등급/코드 유일, 관리 전용/준비 상태를 보존하라. 기획안 12.10의 계약을 요청 경계·서비스·비동기 작업에 적용하라.

8. 공통 데이터·AI·작업 구조

- 원본 파일, 구조화 데이터, 재사용 양식, 산출 파일, 버전을 분리한다.
- Workspace, BusinessScope, SpreadsheetBook, CrmSpace, CrmRecord, Project, BusinessPartner, Contact, Dataset, SchemaVersion, FormTemplate, FormulaDefinition, Document, ArtifactVersion, Asset, CalendarEvent, Job, Connection, AutomationRule을 공통 기반으로 설계한다.
- 같은 사업의 CRM과 일정은 명시적으로 연결한 공통 거래처를 참조하고, 엑셀과 보고서는 허가된 데이터셋을 공유한다. 사업/CRM이 다른 고객을 이름이나 이메일로 자동 병합하지 않는다.
- 열 이름 대신 불변 field_id로 데이터·계산·뷰·자동화를 연결한다. 표시명/순서 변경으로 값이 사라지면 안 된다.
- 필드 삭제/타입 변경/대량 갱신 전 영향과 실패 행을 보여주고 되돌리기/보관을 제공한다.
- 모든 업무 객체·파일·캐시·검색·비동기 작업은 workspace 범위로 접근을 제한한다. 요청의 workspace_id를 신뢰하지 않는다.
- AI는 해석·추출 후보·추천·문장·구성을 담당하고 서버는 인증·권한·저장·계산·파일 생성·결제·발송을 담당한다.
- OpenAI Responses API 기반 어댑터와 구조화된 응답 계약을 권장한다. 모델명·추론 강도·지원 기능·한도를 실제 계정/공식 문서로 확인한다. 개발용 Astra High 선택과 운영 API 모델 설정을 혼동하지 않는다.
- JSON 스키마 준수는 사실성·권한·금액 정확성의 보장이 아니다. 서버 검증을 거쳐 실행한다. 거절·잘림·잘못된 참조를 처리한다.
- 첨부 문서의 지시를 시스템 명령으로 취급하지 않는다. 다른 고객 정보, 비밀값, 임의 SQL/명령 실행 권한을 AI에 부여하지 않는다.
- 작업 상태: DRAFT/NEEDS_INPUT/READY/QUEUED/RUNNING/REVIEW_REQUIRED/SUCCEEDED/FAILED/CANCELLED.
- 작업 ID·입력 버전·흐름/프롬프트/모델 버전·재시도·사용량·오류·출력 버전을 기록한다.
- worker 재시작 시 작업이 복구되고, 중복 선점/실행을 제어한다. 메모리 상태만으로 긴 작업을 운영하지 않는다.

8-1. 다중 양식·CRM과 사업 범위
- 하나의 workspace에 기본 BusinessScope를 만들고 사업이 하나이면 추가 선택 없이 시작한다. 필요할 때 사업을 추가해 구분한다.
- 사업 안에 여러 SpreadsheetBook과 CrmSpace를 만든다. CRM 하나를 만들 때 새 계정/구독을 자동 생성하지 않는다.
- 양식별 데이터·스키마·수식·보기·대시보드·출력, CRM별 등록 데이터·필드·상태·메모·보기·위젯·자동화를 독립 관리한다.
- 1차 엑셀 관리 단위는 양식당 주 데이터셋 하나이며 출력 집계 시트는 파생 결과다. 복잡한 파일의 여러 데이터 영역은 명시적으로 매핑한다.
- 같은 사업의 거래처는 사용자가 연결한 경우에만 공통 연락처를 재사용한다. 다른 사업의 고객/첨부/AI 참조/발신 계정을 섞지 않는다.
- workspace_id+business_scope_id+book_id 또는 crm_id 범위를 서버·파일·캐시·AI·작업·실시간 이벤트에서 검증한다.
- 플랜별 양식/CRM/사업 수·행/고객 수·용량은 설정화하고 숫자는 미정으로 둔다. 한 개 고정 구현은 금지한다. 다운그레이드로 기존 자료를 삭제하지 않는다.
- snapshot, dataset_generation, draft_change_set, formula_dependency, import_job, resource_usage, layout_template, dashboard_definition/widget/aggregate_snapshot을 필요한 저장 모델에 반영한다.

8-2. 질문·업무 이해·추천·내 양식 저장
- WorkSession에 목적·대상·입력/출력·반복 방식·답/근거/상태·남은 질문·선택 양식 버전·사용자 수정을 구조화한다. 대화 전문만 저장해 매번 재해석하지 않는다.
- WorkflowDefinition/Version의 필수 정보와 분기 안에서 AI가 아직 부족한 중요 정보를 다음 질문으로 제안하고 서버가 검증한다. 질문 계약: ID, 대상 정보, 입력 유형, 선택지, 추천/이유, 필수/생략 조건, 검증, 근거/상태.
- 사용자가 요약을 바꾸면 의존한 제안만 무효화/재질문한다. AI 추정을 확인된 사실로 저장하지 않는다. 실패 시 기본 질문으로 이어간다.
- 내 양식은 목적·구조·보기·스타일·기본값·검증·수식·출력·허용된 데이터 연결의 버전이며 실제 고객/행 데이터와 별개다. 구조 복제가 기본, 데이터 복사는 명시적 선택.
- 내 양식 추천은 접근 가능한 사업/업무를 먼저 필터한 뒤 목적·입력 필드 적합성·최근 사용·즐겨찾기로 정렬한다. 이유와 대안을 보여주고 거절 후보를 반복하지 않는다. 적합한 후보가 없으면 새로 만들기를 제안한다.
- 추천은 자동 적용/발송이 아니다. 한 번의 수정으로 전역 취향을 몰래 바꾸지 말고 ‘내 기본 양식으로 저장’에서 범위를 명시한다. 다른 사업으로 복제 시 원사업의 자료·고객 ID·발신 계정 재연결 금지.
- 선택 대상 편집은 object_id/base_version/selection_scope/허용 변경/의존 항목/예상 결과로 검증한다. 직접 편집과 AI가 같은 초안·확정 API를 사용하고 겹치는 제안 취소/동시 수정을 처리한다.
- 조건은 타입이 있는 제한된 규칙 트리와 불변 필드 ID로 관리한다. 깊이/개수/연산 한도, 빈값/날짜/비교 의미를 정의하고 임의 eval/JS/SQL을 실행하지 않는다.
- 신규 논리 객체와 기존 Job/FormTemplate/SchemaVersion의 중복을 정리해 P0에 확정한다. 일반 조회/편집/로그인/정확한 숫자 변경/저장 양식 재사용 자체에 매번 AI 호출을 강제하지 않는다.

9. 엑셀 작성과 데이터 분석의 기본 경로

- 엑셀 메뉴는 오버뷰와 엑셀 목록을 구분한다. 목록 한 항목은 파일 다운로드 이력이 아닌 헤더·데이터·수식·보기·대시보드를 가진 SpreadsheetBook이다.
- 목록에서 엑셀명/행을 누르면 상세의 HTML 엑셀 편집을 바로 연다. 개별 대시보드를 의무 중간 단계로 넣지 않는다. 목록 왕복 시 검색/필터/정렬/스크롤 복원.
- 저장된 상세는 원본 테이블 대시보드로 연다. 원본 편집은 저장 데이터의 변경, 조회 조건/정렬/보고서는 보기의 변경이다. 필요한 도구를 선택할 때만 패널을 펼친다.
- 다중 엑셀의 오버뷰/목록은 수·행 수·검수·갱신·상태·즐겨찾기를 제공한다. 다른 의미/통화/기간의 값을 합치지 않는다. 구조 복제가 기본이며 데이터 복제는 명시 선택.
- 전체 공통 기술·검수 요구는 아래 생성/편집/입출력/분석 모두에 적용한다.
- 전표 헤더와 품목 행, 소계·이월·반복 머리글을 구분한다. 모호한 값은 추측 확정하지 않는다.
- 각 추출값에 원본 파일·페이지·영역·원문·정규화 값·검수 상태를 연결한다.
- 날짜·전화·사업자번호·금액·음수·단위·앞자리 0을 올바른 유형으로 처리한다. 돈은 BigDecimal/Decimal로 계산한다.
- 수량×단가와 합계 비교, 세금 포함 여부, 필수값 누락, 형식 오류, 동일/유사 전표 중복 후보를 검증한다.
- 파일 해시와 업무 키를 함께 사용하고 다른 파일명/재촬영으로 중복 누적되지 않게 한다.
- 첫 양식은 중요 값을 검수하고, 반복 업로드는 이상값 중심으로 검수량을 줄인다. 보류 데이터는 확정 집계에 섞지 않는다.
- ‘엑셀 폼 1’에 매핑·항목 유형·검수 규칙·출력 스타일·분석 설정을 버전과 함께 저장한다.
- 헤더 추가·명칭·순서·너비·숨김·고정·유형·필터·정렬·계산항목을 UI와 자연어로 편집한다.
- 대시보드의 합계·증감·추세는 검증된 쿼리/계산기로 계산하고 AI는 근거와 함께 설명한다. 근거 없는 인과관계를 사실로 만들지 않는다.
- XLSX는 실제 편집 가능한 셀·수식·표시 형식·필터·틀 고정·인쇄 범위를 포함한다. 사용자 텍스트의 수식 주입을 방지한다.
- 외부 수정 파일을 다시 가져오면 변경점·중복·충돌을 확인한다. 모든 Excel 기능의 무손실 왕복 편집을 약속하지 않는다.

9-1. 엑셀 생성의 방식 — 사진/대화/직접 입력/Excel 가져오기
- ‘엑셀 생성’→사진 업로드/채팅을 통해서/직접 입력. 세 경로는 같은 HTML 편집기·초안/저장 모델을 쓴다. 새 엑셀 생성과 기존 엑셀 데이터 업로드를 구분한다.
- 사진: 사진 1장/여러 장→검사/원본 보관→GPT 분석→헤더 추천과 실제 데이터 입력→원본 대조 초안→검수/수정→저장. 헤더만 만들고 사용자가 사진의 값을 재입력하게 하지 않는다.
- 사진 값은 원본 영역/페이지와 연결하고 불명값은 확인 필요로 둔다. 여러 표의 구조가 다르면 매핑/분리를 제안한다. 미검수 값과 샘플을 확정 집계에 섞지 않는다.
- 채팅: 간단한 질문/선택지→목적/기록 파악→헤더/유형/설명 제안→‘더 이야기하기’ 또는 ‘현재 제안으로 결정’→선택 제안의 엑셀 초안→저장.
- 더 이야기하기는 제안을 보존해 구체화하고 변경된 헤더를 표시한다. 이전안 재선택 가능. 현재 제안으로 결정은 현재 선택 proposal/version으로 즉시 초안을 열며 추가 설문을 강요하지 않는다.
- 생성 가능 정보가 있으면 먼저 제안하고 사용자가 대화를 계속할지 고른다. 필수 정보가 없는 경우만 이유와 질문을 보여준다. 결정 중복 클릭/늦은 AI 응답이 중복 생성·오래된 안 덮어쓰기를 일으키지 않는다.
- 채팅에서 헤더만 정했다면 실제 데이터는 빈 상태다. 샘플 행은 예시로 구분해 저장/집계 제외. 사용자가 실제 데이터를 제공한 경우 입력 행을 검토할 수 있게 한다.
- 직접 입력: 빈 HTML 엑셀→헤더 셀에 이름→아래 행 데이터/붙여넣기→검증→저장. AI 응답이나 별도 헤더 마법사를 기다리지 않는다.
- 열 문자/행 번호·활성 셀·편집 입력줄·스크롤·범위 선택, 타이핑·더블클릭·Enter/Tab/방향키, 행/열 추가/삭제·복사/붙여넣기·되돌리기를 제공한다. 셀 값 지우기와 행/열 삭제를 구분한다.
- 새 헤더는 불변 field_id를 생성하고 라벨/순서 수정은 ID를 보존한다. 무명 데이터 열은 헤더를 안내하고 타입 추정은 검증한다. 전화번호/코드 앞자리 0 보존.
- 신규 ‘저장’은 최초 확정이다. 하나 이상 유효 헤더가 있으면 데이터 0행 양식 저장 가능. 생성 방식 전환은 기존 초안 유지/버림을 분명히 한다. PDF/XLSX/CSV 보조 가져오기를 유지하되 세 생성 선택지를 혼동시키지 않는다.

9-2. 상세 HTML 엑셀과 적용
- 목록 선택 시 저장 헤더/데이터를 실제 편집 가능한 Thymeleaf 업무 화면에 연결한 HTML/JavaScript 그리드로 조회한다. 이미지 미리보기나 가짜 데이터로 대체하지 않는다.
- 헤더 생성/이름/위치/너비/숨김/고정/유형, 셀/행 CRUD·범위 붙여넣기·검색/필터/정렬, CRM식 행 상세 폼을 같은 데이터 위에서 제공한다.
- ‘적용’은 헤더·데이터·수식의 현재 변경 집합을 검증하고 서버 DB에 확정하는 버튼이다. 성공 후 화면 닫기/재접속/재조회/다운로드/오버뷰/대시보드/분석 결과가 같은 버전이어야 한다.
- 미적용/적용 중/적용됨/실패 상태와 변경 셀/행/필드·오류·영향을 표시한다. 일반 편집은 한 변경 묶음의 일관된 확정이 기본이며 실패 시 기존 확정본 유지.
- 전체 변경 취소는 마지막 확정 버전으로 복귀. AI의 이번 제안 취소는 해당 변경만 제거하고 기존 수동 초안 보존. 이동은 적용 후 이동/초안 유지/버리기를 구분한다.
- 필드 삭제/타입 변경 전 수식/분석/폼/실패 행 영향 검사. 이름/순서 변경으로 값·참조를 잃지 않는다. 동시 저장은 기준 버전 충돌, 중복 적용은 멱등 처리.
- 화면 로드 행과 전체/필터/선택 범위를 구분하며 대량 데이터는 가상화/서버 페이징. 직접 편집·저장에 매번 AI를 호출하지 않는다.

9-3. 빈 양식과 데이터 다운로드 및 추가 리셋 업로드
- ‘데이터 입력용 양식 다운로드’는 헤더·입력 형식·안내·지원 수식 구조가 있는 빈 XLSX다. 추가와 리셋 모두에 쓰며 다운로드만으로 서버 무변경. 이전 ‘리셋용 다운로드’ 명칭을 이것으로 통일한다.
- ‘현재 데이터 포함 다운로드’는 확정 헤더/데이터/수식/서식이다. 기본 전체, 현재 필터/선택은 명시 선택. 미적용 값이 포함된 것처럼 표시하지 않는다.
- 빈 양식 채움→해당 엑셀 업로드→대상과 추가/전체 교체(리셋) 선택→파일 검사/매핑→변경 결과 검토→추가 적용/리셋 적용. 드롭 먼저 해도 실행 전 모드 확인. 모드 변경 시 검증/미리보기 재계산.
- 추가는 기존 행 보존·새 행 추가·중복 검수이며 기존 값을 몰래 갱신하지 않는다. 리셋은 선택 엑셀의 활성 업무 데이터 전체 교체이며 현재 필터에 보이는 행만 바꾸는 동작이 아니다.
- 빈 입력용 파일은 실제 고객/거래 데이터 잔존 금지. 계산 열/입력 열과 필수/단위를 안내하고 업로드 캐시 계산값은 서버에서 재계산한다.
- 메타데이터의 양식/스키마/필드 ID는 서버 범위/권한과 대조한다. 외부 파일은 매핑·누락·타입·구버전 검증. 파일만 보고 스키마를 파괴하지 않는다.
- 리셋 전 N건→M건·제외 건·연결/자동화 영향을 확인한다. 0건 파일은 기본 거절, 전체 비우기는 별도. 신규 빈 양식 저장과 구분한다.
- 서버 스냅샷→임시 영역 검증/계산→원자적 활성 버전 전환. 실패 시 기존 유지, 중복 요청 방지, 미리보기 이후 동시 변경 검사. 양식 ID/수식/보기/대시보드 보존, 다른 엑셀/CRM 무변경.
- 과거 행 참조는 당시 버전/보관 행을 유지하고 새 행에 임의 연결하지 않는다. 수동 고정 분석 범위도 리셋 영향 검사. 과거 업로드로 의도치 않은 자동 발송 금지.
- 미적용 편집 중에는 적용 후 계속/확정본 기준/취소를 구분한다. 확정본 기준에서도 초안은 버리지 않고 import로 버전이 바뀌면 재검토한다.
- 복구 전 현재 변경과 차이를 확인하고 복구 직전 상태도 보관한다. 일반 XLSX만으로 내부 ID/모든 이력 복원 보장 금지.

9-4. 완성된 엑셀의 수식 대화
- 엑셀 상세→수식 버튼→해당 엑셀/선택 범위 대화→요청→필요 조건 질문→GPT 수식/예상값→더 이야기하기 또는 수식 넣기→실제 셀/계산 열에 초안 삽입→적용.
- 설명/복사용 문자열로 끝내지 말고 검증된 수식을 직접 편집기에 넣는다. 현재 엑셀의 실제 필드/셀을 참조하고 미적용 변경 포함 여부와 기준 버전을 표시한다.
- 월급=원/월·기간=개월 수로 확인되면 총액=월급×복무개월수. 3,000,000×12=36,000,000 예상값을 제시한다. 날짜 구간/일할/단위 등이 불명확하면 질문하며 실제 급여 세금/수당까지 자동 포함했다고 표현하지 않는다.
- 특정 셀과 전체 행 계산 열을 구분하고 새 열 이름/위치·입력 필드·영향 행·단위·빈값·반올림·예상 결과를 보여준다. 이미 확인한 조건은 다시 묻지 않는다.
- 수식 넣기는 초안 변경이며 적용으로 확정. 제안 취소는 해당 제안만, 전체 취소는 전체 편집 초안만 제거. 저장한 계산 열은 새 행/추가 업로드와 입력 변경에도 재계산.
- 직접 수식 편집도 같은 검증을 거친다. 수식 입력줄/명시적 수식 편집과 일반 텍스트/붙여넣기를 구분한다. 계산 셀은 기본 읽기 전용이며 수식 수정 또는 명시적 값 전환을 사용한다.
- 대량 계산은 성공한 버전만 활성화하며 실패 시 이전 데이터/수식 유지. 구두 입력은 음성 전사 후 이름/숫자/단위 확인, 실패 시 텍스트로 이어가는 기존 요구 유지.
- 허용 연산/함수만 파싱해 실행하고 eval/임의 SQL/시스템 명령은 금지한다. field_id와 record_id+field_id 참조로 열명/순서 변경에도 의미를 보존한다.
- 순환·없는 참조·0 나눔·빈값·타입·날짜·정밀도·반올림·필터/숨김 행 집계 범위를 검증하고 오류를 0으로 숨기지 않는다.
- Excel 내보내기는 검증된 동등 수식과 서버 결과를 대조한다. 지원하지 않는 함수·외부 참조·양식 간 임의 수식은 대안을 안내한다. 값 출력이면 수식 보존으로 표시하지 않는다.

9-5. 데이터 보기와 그래프의 정확한 순서
- 저장 완료→원본 테이블 대시보드를 즉시 표시한다. 조회·정렬·계산 열·보고서·다운로드 중 필요한 행동을 선택하면 관련 패널을 연다. 보고서는 X/Y 여러 항목과 AND 조건을 설정해 표·그래프로 확인하고 필요할 때 이름별 보기를 저장한다. 보기 저장은 원본 확인의 선행 조건이 아니다.
- 기준: 날짜별 변화(날짜+숫자), 분류별 비교(분류+숫자/건수), 비중(분류+합산 수치), 분포(숫자), 두 숫자의 관계(동일 행의 두 숫자). 데이터 유형에 맞는 기준/차트를 추천한다.
- 예: 월별 출고금액→출고일 열→공급가 열→월/합계/기간→그래프. 분류별 비교면 거래처/품목과 집계값을 고른다. 없는 지표를 만들지 않는다.
- 필요한 역할만 한 단계씩 질문하고 선택지 또는 미니 그리드의 열/셀 선택을 지원한다. 선택 범위 색·헤더·A1 주소·행 수·역할을 보여준다. 범위 크기/행 대응/유형·헤더/소계 제외를 검증한다.
- 전체/현재 필터는 동적 범위, 직접 선택 행/셀은 안정된 ID의 고정 범위가 기본이다. 선택 조건·신규 포함 여부를 저장하고 정렬 때문에 다른 행을 가리키지 않는다. 현재 페이지만 집계해 전체라고 표시하지 않는다.
- 집계/기간 포함 경계/시간대/단위/빈값/제외 행/비중 분모를 명시한다. 혼합 통화, 숫자 아닌 값, 비중의 음수/합계 0 등은 왜곡하지 말고 오류/대안을 제시한다.
- 선/막대/도넛 또는 누적 막대/히스토그램/산점도는 기준에 맞게 추천하고 변경 가능하게 한다. 서버가 집계, GPT는 추천/설명 담당. 원인을 근거 없이 확정하지 않는다.
- 그래프+집계표+근거 행 조회·적용 조건·데이터 버전·갱신 시각을 제공한다. 막대/점에서 실제 데이터로 이동한다.
- 보기 저장은 이름·기준·범위·축/값·집계·필터·차트 표현을 저장하고 원본 무변경. 엑셀 하나에 여러 보기·복제/수정/삭제 가능, 해당 대시보드 표시도 선택. 표 표시 보기와 분석 보기를 타입으로 구분한다.
- 적용/import 후 확정 버전의 보기/대시보드를 갱신한다. 초안은 명시된 미리보기만 허용한다. 필드 삭제·타입 변경·리셋으로 고정 행 참조가 없어지면 재선택 안내, 임의 재연결 금지. 데이터 없으면 빈 상태.

9-6. 엑셀의 쉬운 질문과 세밀한 설정
- 열 선택 시 이름/위치/표시, 자세히 조정에서 타입/단위/소수점/반올림/빈값/필수/허용 범위/계산을 보여준다. 표시용 반올림과 계산 반올림을 구분한다.
- 월급×기간은 현재 필드에서 단위가 확정되면 다시 묻지 않는다. 날짜 구간이면 환산/일할 기준 등 미확인만 질문하고 예시 결과를 보여준다.
- 그리드/행 상세 폼/출력용 엑셀의 표시 설정을 분리하되 데이터 정의는 공유한다. 열 숨김을 데이터 삭제나 출력 열 자동 삭제로 처리하지 않는다.
- 입력 폼은 순서/묶음/설명/조건 표시를 지원한다. 가져오기 매핑은 양식 버전과 원본 헤더에 묶어 재사용하고 변경된 부분만 묻는다.
- 대시보드는 원하는 수치→필요한 집계/기간/그룹/빈값→표현으로 순차 조정한다. 처음부터 전체 위젯 설정표를 펼치지 않는다.

9-7. 상태와 API 납품 기준
- 헤더 제안의 proposal/version, 편집 초안의 draft/base_version, 확정 book/schema/data_version, 분석 view/definition_version을 구분한다. API는 사용자 범위/권한을 모두 검사한다.
- 세 경로 초안 생성, 사진 작업/원본 연결, 채팅 추가 대화/선택안 결정, 신규 저장, 셀/행/헤더/수식 변경 검증/적용/취소, 빈/데이터 export, 추가/리셋 계획/검수/확정/복구를 제공한다.
- 분석 가능 역할 조회·필드/범위 검증·집계 미리보기·그래프 데이터·보기 CRUD/복제·근거 행 조회 API를 명세한다. 정의에 범위 모드·불변 필드/행 ID·필터·집계/기간/단위·차트를 저장하고 집계 응답은 버전/포함·제외 건수/경고를 포함한다.
- 버튼의 의미: 더 이야기하기=대화; 현재 제안으로 결정=선택안으로 엑셀 초안; 저장=신규 확정; 수식 넣기=수식 초안; 적용=기존 엑셀 변경 확정; 그래프 보기=조회; 보기 저장=분석 설정 저장. 화면과 API/DB가 같은 의미여야 한다.

10. 워드 한글 PPT

- 각 메뉴에 오버뷰/목록/새 문서를 제공한다. 목록 선택은 실제 편집 상세로 연결한다. 중앙 페이지/슬라이드, 왼쪽 개요/썸네일, 선택한 때의 속성/AI 패널을 제공하고 버전/리소스/레이아웃/출력은 상세 안에서 연다.
- 새 문서: 사진 업로드/채팅으로 만들기/직접 작성→필요한 질문/자료 검수→편집 초안→저장. 기존 문서도 같은 편집기를 사용한다.
- 사진은 여러 장의 순서·회전·자르기와 내용 옮기기/구성 참고/이미지 삽입 목적을 확인한다. GPT로 글/표/목록/읽기 순서를 추출하고 원본 영역과 대조한다. 불명확한 값은 확인/미확인으로 남긴다. 문서 전체를 이미지로 붙이고 편집 가능한 생성이라고 하지 않는다.
- 채팅은 목적/독자/핵심 내용/분량을 필요한 만큼 묻고 개요에 더 이야기하기/현재 제안으로 결정을 제공한다. 결정 즉시 선택 제안의 초안으로 간다. 가격·조건·연락처·실적·통계를 창작하지 않는다.
- 직접 작성은 빈 문서/내 양식에서 즉시 입력한다. AI 없이 글 입력/수정/삭제, 표 삽입과 행/열/셀 편집, 도형/글상자/이미지 삽입·교체·삭제, 실행 취소/다시 실행이 가능해야 한다.

10-1. 실제 객체의 정밀 편집
- 글: 글꼴/크기/강조/정렬/색/문단 스타일/간격/들여쓰기. 표: 행/열/값/너비/병합/해제/여백/테두리/배경/반복 머리글. 도형: 사각형/원/선/화살표/글상자, 채우기/테두리/회전/크기/정렬/그룹/잠금. 이미지: 비율/자르기/초점/교체/포맷별 배치.
- PPT: 슬라이드 추가/복제/삭제/순서/레이아웃, 자유 배치 좌표/간격/레이어/테마 범위, 편집 가능한 차트와 근거 데이터. 16:9 권장, PPTX 필수. Word/HWP: 문단 흐름·용지/방향/여백/구역/머리말/꼬리말/쪽 번호/페이지 나눔. 동일 좌표 캔버스로 대체하지 않는다.
- 위 항목은 목표 지원표다. 기본 글 수정·표/도형 삽입이 안 되는 엔진은 핵심 요구 미완료다. 고급 옵션도 실제 저장/출력 지원을 확인하고 미지원은 안내하라. 웹에서만 보이는 가짜 편집은 금지한다.
- AI는 선택한 문단/표/슬라이드/객체와 기준 리비전을 사용해 수정안→반영/제안 취소→초안 확인→변경사항 저장으로 처리한다. 선택 밖/잠금/기존 수동 초안을 보존하고 늦은 응답은 충돌 검사한다. 직접/AI 변경은 같은 원본과 검증된 편집 명령을 쓴다.
- 한글 출력은 실제 HWP다. HWPX/DOCX 확장자 변경이나 이미지 문서로 대체하지 않는다. P0에서 직접 편집·AI 부분 수정·도형/표·저장/렌더링·Ubuntu·SaaS 사용/동시 처리/라이선스를 검증한다. 엔진 미확보는 준비 중/미완료이며 유료 제공 완료로 표시하지 않는다.

10-2. 문서 버전 리소스 레이아웃
- 최초 저장 V1, 이후 변경사항 저장 V2, 초안 자동 보관과 구분한다. 버전별 기반 버전/변경 요약/출력 상태/비교/미리보기/다운로드를 제공한다. 과거 복원은 새 초안으로 시작하며 기존 확정본/발송본을 덮지 않는다.
- 출력은 document_revision+format+renderer_version+export_revision에 고정한다. 서버 저장과 파일 생성 완료를 구분하며 출력 실패 시 기존 자료를 보존한다. 같은 파일 재다운로드는 보관된 바이트를 제공한다.
- 리소스의 사용 위치/용량/버전/다른 문서 영향을 표시하고 AI 사용량과 구분한다. 대시보드에는 새 작업용, 상세에는 현재 내용용 추천을 소수 미리보기/이유로 제공한다.
- 레이아웃 변경은 내용/수동 편집/넘침을 확인해 초안 반영 후 저장한다. 내 양식/레이아웃에는 구조/브랜드/자리표시자/허용 데이터 연결을 저장하고 실제 고객정보를 기본 복제하지 않는다.
- 저장한 엑셀 분석 표/차트, CRM 고객, 일정 정보를 권한 범위에서 문서로 가져온다. 기본 스냅샷의 원본 ID/버전/조건/시각을 기록하고 최신 자료로 갱신은 변경 확인 후 새 버전이다. 문서 편집이 원본 수정·외부 발송을 자동 실행하지 않는다.
- 외부 편집 파일 재업로드는 별도 가져오기이며 모든 임의 문서의 완전 왕복 호환을 보장하지 않는다.

10-3. 편집 엔진 완료 기준
- 파일 생성기만으로 문서 편집을 완료하지 마라. 브라우저 편집 엔진+AI 명령 어댑터+서버 저장+출력 경로가 필요하다. ONLYOFFICE Docs/한컴 웹한글 등 공식 자료는 후보 근거일 뿐 라이선스·기능 충족은 채택 제품/버전으로 확인한다.
- 포맷마다 하나의 편집 원본을 정하고 엔진 문서와 자체 구조 모델을 각각 수정해 덮어쓰지 않는다. AI 선택 앵커가 유지되지 않으면 기준 버전과 대상을 다시 확인한다.
- 포맷×기능×직접×AI×저장 재열기×출력 지원표를 P0에 작성한다. 저장 콜백 인증/세션/버전/중복 검사, 안전한 파일 보관 후 확정 연결을 구현한다. 자동 저장을 초안으로 받고 사용자 확정 저장과 구별할 수 있는지도 시험한다.
- 실제 Word/PowerPoint/한글에서 글·표·도형을 각각 선택해 수정하고 저장/출력한 결과까지 검수한다. 저장 성공 토스트만으로 완료 판정하지 않는다.

11. 간단한 프로그램 만들기

- 오버뷰/프로그램 목록/새 프로그램→상세 부품 목록과 동작 미리보기→직접/AI 변경→변경사항 저장→V1/V2→빌드/검수→다운로드가 기본 경로다. 최신 저장 버전과 활성 버전을 구분한다.
- 신규는 질문으로 만들기/사진으로 설명하기/부품 직접 구성. 질문은 줄일 업무→기기→혼자/공동→온라인/오프라인→입력/출력이다. 사진에서 화면/양식 후보를 추출하되 보이지 않는 계산·저장·권한은 질문한다. 현재 제안으로 결정은 선택 제안의 초안 생성이다.
- 권장 1차는 검증된 폼/표/계산/차트/출력/승인/업무 규칙을 조립한 브라우저 앱이다. 내부 실행과 별도로 버전별 실행 패키지 다운로드를 필수 구현한다. 구성 JSON이나 링크만 제공하고 완료하지 않는다.

11-1. 부품 관리
- 사용자 요청을 고객 입력/상품 목록/합계 계산/명세서 출력/저장 버튼/권한 같은 업무 부품으로 저장한다. 불변 ID·종류·설명·순서/화면·입출력·데이터·검증/표시 조건·의존성을 관리한다.
- 목록/미리보기 선택이 같은 설정으로 연결되고 부품 추가/수정/삭제/순서 변경을 직접 또는 AI로 수행한다. AI 변경안은 해당 부품/기준 리비전에 적용하며 선택 밖·잠금·수동 입력을 보존한다.
- 삭제는 참조 영향과 대체/연결 해제/함께 변경 범위를 확인한다. 화면 제거와 실제 필드/업무 데이터 삭제를 구분한다. 이름 변경은 기존 ID와 값을 유지한다.
- 시험 데이터/실행을 실제 DB/외부 발송/결제와 분리한다. 허용 부품과 안전한 계산 엔진만 쓰며 임의 JS/SQL/eval/생성 코드를 운영 프로세스에서 실행하지 않는다.

11-2. 버전 생성 빌드와 활성화
- 최초 확정 저장 V1, V1에서 수정 후 변경사항 저장 V2. 초안 자동 보관/키 입력/AI 응답마다 버전을 만들지 않는다. 변경 없음은 새 번호 없음, 중복 클릭은 멱등 처리다.
- 검증→불변 스냅샷/버전 할당→격리 빌드·검수→패키지 보관→다운로드 가능. 검증 실패는 초안, 할당 후 빌드 실패는 그 버전의 실패 상태다. 재시도는 동일 스냅샷이며 내용 변경은 새 버전이다.
- 버전 목록: V번호·기반 버전·시각·변경 요약·부품 변경·빌드 상태·데이터 호환·활성 여부·미리보기/다운로드/비교/복원. 실패 파일에 다운로드 성공 표시하지 않는다.
- 저장/다운로드와 이 버전 사용을 구분한다. 활성화 전 데이터 변환·기존 필드/참조·권한·백업을 검사한다. V1 복원은 V1 기반 새 초안→V3 등 새 버전이며 설정/데이터 복원은 별개다. 호환 검사 없이 다운그레이드하지 않는다.

11-3. 실행 패키지와 프로그램 현황
- 권장 ZIP: 해당 앱 정의+고정된 검증 런타임+실행 산출물+해당 앱 전체 소스+빌드/실행 안내+필요 DB migration+빈 설정 예제+의존성/라이선스+체크섬. 깨끗한 지원 환경에서 설명대로 실행 가능해야 한다. 불필요한 DB를 요구하지 않는다.
- 플랫폼 전체 개발 소스 ZIP과 고객용 앱 버전 ZIP은 다르다. 고객 ZIP에 타인 앱/자료·실제 비밀값·운영 데이터·플랫폼 관리 코드를 넣지 않는다. 외부 API/플랫폼 전용 기능 의존성을 표시하고 발급값을 별도로 설정한다. 배포 가능한 라이선스를 확인한다.
- V1 재다운로드는 보관된 V1 파일이다. 같은 버전 재빌드 변경은 별도 빌드 리비전/체크섬/이유를 남기고 기존 파일을 보존한다. 외부 실행 환경 업데이트는 지원 원본 버전·백업/적용/복구를 명시한다.
- Windows 사용과 EXE/오프라인은 구분한다. EXE/Mac/완전 오프라인/자동 업데이트는 OS별 패키징/서명/로컬 데이터/동기화 검증이 필요한 별도 대상이다. 웹 ZIP으로 대체 완료하지 않는다.
- 오버뷰는 프로그램 수, 상세 버전은 그 프로그램의 이력이다. 실제 수집한 실행/입력/오류만 현황에 표시하고 외부 실행 미수집은 미집계다. 복제는 새 프로그램 ID/V1에 구조만 기본 복사한다.
- P6 완료는 부품 변경→V2 저장→실제 파일 다운로드→새 환경 실행→입력/저장/재조회/출력 및 V1/기존 데이터 보존까지다.

12. CRM

- 업종/목적 → 추천 항목 → 추가 항목 → 목록 미리보기 → 기존 자료 가져오기/등록 → 저장의 순서.
- 회사/거래처와 담당자/개인 고객을 구분하고 한 거래처의 복수 담당자를 지원한다.
- 이름·전화·이메일·주소·상태·태그·담당자·최근 연락·다음 할 일·메모를 기본으로, 사용자 정의 항목을 추가한다.
- 항목 유형·필수·중복·기본값·선택값을 정의하고 목록/입력/검색/내보내기에 같은 정의를 쓴다.
- 열 표시·명칭·순서·너비·고정·숨김, 필터·정렬·그룹, 저장한 보기를 제공한다.
- 상세에는 상담 타임라인, 공통 메모, 파일/문서, 일정, 발송 이력을 보여준다.
- 가져오기는 자동 열 매핑→오류/중복 확인→신규/갱신 구분→적용. 이름만 같은 고객을 자동 병합하지 않는다.
- 병합·삭제·일괄 변경은 연결 자료의 영향을 보여주고 이력·복구를 고려한다.

12-1. 다중 CRM 오버뷰·독립 관리
- 같은 계정에서 여러 CRM을 만든다. 사업·고객 종류별 항목/등록 데이터/상태/메모/보기/위젯/자동화를 독립 관리한다.
- 전체 오버뷰에 CRM별 고객 등록 수·신규/수정·후속 연락 필요·기한 경과·예정 일정·발송 실패 등을 제공하고 사업/기간/상태 필터를 지원한다.
- CRM 목록의 카드/이름을 누르면 해당 CRM 상세의 고객 목록, 지표를 누르면 해당 조건의 고객 목록/근거로 이동한다. 개별 대시보드는 상세 안의 현황 탭이다.
- 개별 대시보드는 상태 분포·추이·할 일·최근 활동·예정 일정을 제공하고 실제 존재하는 필드에 맞는 위젯을 추천한다.
- ‘고객 등록 건수’는 CRM 레코드 합계, 중복 제외 수는 명시적으로 연결된 같은 사업의 공통 거래처 ID 기준으로 구분한다. 이름/이메일로 자동 중복 제거하지 않는다.
- 고객 추가/수정/삭제/import 확정 시 오버뷰와 개별 현황을 갱신한다.
- 복제 기본은 구조만 복사. CRM 보관/삭제가 다른 CRM의 자료/공유 거래처/일정을 지우면 안 된다.
- 발신 계정과 수신 동의의 주체·채널·목적을 사업/CRM 범위에 맞게 검사하고 다른 사업 계정으로 자동 발송하지 않는다.

12-2. CRM의 질문·입력 폼·목록·조건
- ‘스키마를 입력하세요’ 대신 누구를 관리하고 어떤 일을 놓치는지부터 묻는다. 관련 필드를 추천하고 실제 또는 가상 표시된 한 건으로 미리보기한다. 가상 고객은 실제 집계에 넣지 않는다.
- 목록 헤더/고객 입력 폼/상세 카드에서 해당 항목 설정으로 바로 진입한다. 동일 항목 정의 위에 순서·폭·묶음 등 화면별 표시 설정을 따로 둔다.
- 타입·필수·기본값·선택 옵션·유효 범위·설명·조건 표시를 설정한다. 예: 법인일 때만 사업자번호 표시/필수. ‘항목→조건→값’에서 시작하고 필요할 때 AND/OR를 확장한다.
- 조건 문장·일치/불일치 예시와 결과를 보여준다. 숨김/필수 충돌·조건 순환은 저장 전 차단한다. 숨김으로 기존 값을 지우거나 서버 권한을 우회하지 않는다.
- ‘이번 달 연락할 거래처’ 요청을 날짜/상태/최근 연락 조건으로 제안하고 대상 건수/고객을 확인해 보기로 저장한다. 기간 경계·시간대·빈 날짜 의미를 표시한다.
- 목록에서 고객 상세를 열고 돌아와도 검색·필터·위치 유지. 반복 등록은 저장한 내 폼을 즉시 사용한다. 사업/CRM별 독립성은 기존 기준 그대로 적용한다.

12-3. CRM 생성과 구조 고객 보기 저장
- 오버뷰/CRM 목록/새 CRM→질문 또는 기존 파일/사진 또는 직접 항목 구성→폼/목록 초안→검수→CRM 저장. 사진은 원본과 연락처/불명확 값/중복을 대조하고 항목만 만들기와 검수 고객도 등록을 구분한다. 수신 동의는 임의 생성하지 않는다.
- CRM 상세의 고객 목록에서 고객 상세로 이어지고 값을 직접/AI 수정한다. 구조 변경 적용은 스키마 버전, 고객 저장은 레코드 버전/이력, 보기 저장은 필터/열/정렬/집계 정의다. 고객 한 건 수정으로 CRM을 V2 복제하지 않는다.
- 구조 적용 전 기존 데이터의 타입 변환/필수/중복/계산/자동화 참조를 검증한다. 공통 거래처 변경 영향과 CRM별 상태/메모 독립성을 유지한다. 일괄 고객 수정은 조건·대상 수·변경 값·제외 항목을 보여준 뒤 확정한다.
- 기존 CRM 사진/파일 업로드는 해당 CRM에 매핑/추가/갱신하며 매번 새 CRM을 만들지 않는다. 예시 고객은 실제 집계에 넣지 않는다.
- 분석은 기준→필요 필드→집계/기간/필터→표/그래프→보기 저장. 현재 필드만 사용하고 등록 건수/고유 수의 의미를 표시한다. 위젯은 같은 조건의 고객 목록으로 연결한다.
- 고객에서 일정/문서/연락으로 이동할 때 사업/CRM/거래처 맥락을 이어받고 필요한 입력만 묻는다. 기존 발송 연결·동의·승인/예약 규칙을 보존한다.

13. 일정관리

- 달력 날짜 클릭 또는 거래처 드래그 → 기존 검색/빠른 등록 → 제목/시간/담당자 → 메모/파일/알림 → 저장.
- 거래처를 선택하면 해당 사업과 CRM을 이어받는다. 일정에서 신규 거래처 확정 시 선택 사업 주소록과 선택 CRM에 등록하며, CRM 미선택은 사업 주소록에만 등록한다. 모든 CRM에 자동 추가하지 않는다. 개인 일정은 거래처 없이 가능하다.
- 거래처 공통 메모·공통 파일과 이번 일정만의 메모·파일을 구분한다.
- 일정 상세에서 최신 거래처 연락처·주소·메모·관련 자료를 바로 확인한다. 실제 발송/증빙에 사용한 값은 당시 스냅샷을 보존한다.
- ‘거래처 계정’이 외부 로그인 정보라면 아이디/URL과 비밀번호를 구분한다. 실제 비밀번호는 별도 암호화 보관 기능 없이는 일반 메모/AI 대화에 넣지 않는다.
- 월/주/일/목록, 검색·필터, 드래그 이동·시간 조절, 완료/취소, 반복 일정과 개별 예외를 지원한다.
- 시간대 기본 Asia/Seoul, 서버 UTC+IANA 시간대. 종일 일정은 날짜로 별도 관리한다.
- 반복 일정 변경은 이번 건/이후/전체를 구분하고, 취소된 일정의 예약 발송을 중지한다.
- 1차는 내부 달력. Google Calendar 양방향 동기화는 충돌/삭제/외부 ID/재연결 설계를 거친 후속 범위다.

13-1. 일정 대시보드와 범위
- 오늘/이번 주/미완료/기한 경과/충돌/알림 실패 요약과 달력·목록 전환을 제공한다.
- 사업·CRM·거래처 필터를 제공하고 통합 달력은 접근 가능한 범위만 표시한다. 개별 일정에 사업·CRM을 표시한다.
- 일정↔CRM/고객 상세 이동은 정확한 범위를 유지한다. 사업/CRM 재연결은 첨부·거래처·발신 계정·예약 자동화 영향 확인 후 처리한다.

13-2. 일정의 순차 설정
- 시작 화면의 날짜·시간·거래처를 사용하고 제목/일시/거래처 또는 개인을 먼저 보인다. 반복/알림/메모를 선택한 경우에만 관련 옵션을 펼친다.
- 모호한 날짜는 질문하고 분명한 날짜는 해석한 값/시간대를 보여준다. 시간·길이·상태·반복 종료·알림 시점은 직접 정밀 변경 가능하다.
- 반복 변경 범위·공통 메모/이번 일정 메모를 구분한다. 기본값은 명시적으로 저장한 경우 추천하며 추천만으로 새 일정/발송을 실행하지 않는다.

13-3. 일정의 목록 상세와 사진 대화 편집
- 오버뷰/목록/달력/새 일정과 동일 일정 ID의 상세 편집을 제공한다. 직접 입력/AI에게 말하기/사진에서 가져오기→필요한 확인→초안→저장. 목록과 달력에서 직접 수정/대화 수정이 가능하다.
- 사진 예약표는 후보별 원본·제목·거래처·날짜·시간·반복을 검수하고 연도/오전오후/시간대 모호함을 질문한다. 선택한 확정 후보만 가져오고 중복 후보/부분 실패/재시도를 관리한다.
- 기존 일정 대화는 변경 전후 일시와 반복 범위(이번 건/이후/전체)를 확인한다. 수정안 반영은 초안, 변경사항 저장은 확정이다. 드래그도 동일 검증/저장 경로로 처리하며 반복/알림 영향이 있으면 확인한다.
- 초안 취소는 예약 알림 무변경. 시간 변경/취소/거래처·담당자 변경 확정 시 승인된 예약 알림을 재계산/취소하고 과거 발송과 반복 예외를 보존한다. 다른 일정을 자동 이동하지 않는다.
- 일정 저장은 레코드/반복 이력이며 실행 패키지 버전이 아니다. 공통 거래처 메모/이번 일정 메모·일정 삭제/거래처 삭제를 구분한다.
- 내 일정 양식에는 길이/체크리스트/알림 기본값을 저장하고 특정 날짜/고객을 기본 복제하지 않는다. 상태/거래처별 분석 보기는 기간·취소·종일 기준을 표시하고 근거 목록으로 연결한다.

13-4. 기능 연결과 저장 API
- 엑셀 분석→문서 표/차트, CRM 고객→문서 받는 사람/일정, 일정→안내/결과 보고 초안을 권한 범위에서 연결한다. 기본은 원본 ID/버전/조건/시각을 보존한 스냅샷이다. 갱신은 차이 확인 후 새 초안/버전이며 역수정·외부 발송은 별도 행동이다.
- DocumentRevision/EditorSession/ElementAnchor/AssetRevision/Export, AppComponent/Dependency/Draft/Version/BuildAttempt/Artifact/Deployment/MigrationPlan, CrmSchema/RecordVersion/SavedView, CalendarEventVersion/RecurrenceException/ImportDraft/ReminderPlan의 경계를 P0 ERD에서 기존 모델과 통합한다.
- overview/list/detail/draft/proposal/validate/commit/history/clone/archive와 종류별 저장 API를 정의한다. 객체/사업/기준 리비전/멱등키를 검사하고 직접/AI 편집이 같은 서버 검증을 사용한다. 실제 확정 후 대시보드/목록을 갱신한다.
- 원본 권한 철회 후 신규 조회/갱신을 막는다. 이미 확정된 문서는 별도 문서 권한/보존 규칙으로 관리한다. 복제 기본은 구조만이며 다른 사업에서 자료/발신 계정/거래처 연결을 다시 선택한다.

14. Gmail·Cafe24·SOLAPI 연결과 자동화

- 연결 화면은 설명→서비스 가입/필수 준비→정확한 값 입력→연결 확인→선택한 수신자 테스트→활성화 순서다.
- Google 로그인 권한과 Gmail 발송 권한을 분리한다. 고객 개인 Gmail/Workspace OAuth 연결을 기본으로 하고 최소 gmail.send 범위를 검토한다.
- 고객에게 Gmail 비밀번호를 플랫폼에 입력하도록 요구하지 않는다. refresh token 등은 암호화·마스킹·회수·갱신한다.
- Cafe24는 기존에 제공한 SMSService의 EUC-KR→Base64→form URL 인코딩 및 SMS/LMS 분기 구조를 활용한다.
- 개선 필수: 설정/고객별 연결 주입, connect/read timeout, 번호/인코딩 검증, 목적별 제목, 응답 코드/본문 검사, 실패 전파, 요청 ID, 민감 로그 차단.
- HTTP 200을 발송 성공으로 간주하지 않는다. SMS 길이·LMS 지원·최대 길이·응답 코드는 해당 계정 최신 JSP 예제와 실제 응답으로 확인한다.
- 인증/복구용 플랫폼 문자와 고객 업무용 문자의 계정·비용을 분리한다.
- SOLAPI는 API 인증정보·발신번호·비즈니스 채널·승인된 템플릿·변수 매핑을 설정한다. 채택 버전의 채널 식별 필드와 API를 사용한다.
- 알림톡은 승인 템플릿과 허용 목적에 따라 보내며 자유 텍스트 카카오 메시지와 같지 않다. 광고성/정보성 및 수신 동의/수신거부 정책을 분리한다.
- 일회성 발송은 수신자/본문/템플릿/변수/첨부 버전/예상 건수·비용을 확인하고 실행한다.
- 자동화는 언제/대상/내용/채널/횟수·시간대/취소 조건을 사용자가 승인해 활성화한다. 그 범위 내 반복 실행은 매번 다시 승인받지 않는다.
- 실행 직전에 수신거부·일정 취소·연결 해제·한도·플랜을 재검사한다.
- Outbox, 멱등키, 공급자 접수/전달 상태, 실패/불명 결과를 관리한다. 타임아웃 후 무조건 재시도해 중복 발송하지 않는다.

14-1. 고객용 연결 안내의 편의성
- 이메일/문자/카카오 중 실제 선택한 채널만 준비 안내→값 입력→연결 검사→사용으로 진행한다. 모든 외부 계정을 처음부터 요구하지 않는다.
- 필요한 값의 이름·복사 위치·입력칸·실패 해결을 현재 단계에 보여주고 중단 상태를 이어간다. 콘솔 메뉴는 공식 문서/실제 화면으로 확인한다.
- 키는 전용 마스킹 창에 받고 AI 채팅으로 요구하지 않는다. Google 로그인과 Gmail 발송 권한은 구분하며 연결 검사와 실제 테스트 발송도 구분한다.
- 연결이 없어도 독립적인 CRM/문서 작업은 계속 가능해야 한다.

15. 비밀값과 로컬 직접 입력

- 기존 메시지에 노출된 OpenAI API 키·메일 앱 비밀번호·문자 인증키는 문서/코드/ZIP에 재인용하지 않는다. 사용자는 교체 후 로컬에 입력한다.
- 사용자의 로컬 작업 방식을 존중해 환경변수를 필수로 강제하지 않는다. 서버 전용 LocalSecrets.java 또는 application-local-private.yml 한 곳에서 직접 값을 입력할 수 있게 한다.
- Java 하드코딩을 선택하면 LocalSecrets.java에 모으고 다른 소스에 흩뿌리지 않는다. 배포 ZIP에는 placeholder 예제만 제공한다.
- 실제 값 파일은 Git/공유 ZIP/프런트엔드/로그에서 제외한다. 운영 전환 시 같은 인터페이스로 비밀 저장소/환경변수 사용이 가능해야 한다.
- SMTP 기본값: smtp.gmail.com, 587, auth=true, STARTTLS=true. username/from/app password는 로컬 입력 항목이며 실제 계정 허용 조건을 확인한다.
- 다수 고객의 Gmail/Cafe24/SOLAPI 연결값은 개발자의 로컬 하드코딩과 구분한다. workspace별 암호화 저장과 교체/해제를 구현한다.
- Thymeleaf 모델·렌더링 HTML·JS 인라인·data 속성·정적 JS에 OpenAI·SMTP·SMS·PG 비밀키를 넣지 않는다.

16. 운영·보안·오류

- 모든 업무 API와 파일 다운로드에 인증/소속/권한을 검사하고 테넌트 간 ID 추측으로 접근할 수 없게 한다.
- 운영 HTTPS, HttpOnly/Secure 쿠키, 실제 흐름에 맞는 SameSite/CSRF, 요청 제한, 암호 해시, 최소 DB 권한을 적용한다.
- 업로드 형식·실제 파일·크기·압축 해제 크기·페이지·매크로/악성 자료를 검사한다. 경로 순회·내부망 URL 요청을 차단한다.
- 파일은 비공개 저장하고 변환기는 제한된 실행 환경에서 구동한다.
- 감사 로그·작업 로그·고객 화면 오류 메시지를 구분하고 개인정보·토큰·원문 OTP를 마스킹한다.
- 백업은 DB와 첨부 파일을 함께 복원 시험한다. 삭제/휴지통/탈퇴/보존 정책을 구현한다.
- 개인정보 처리·외부 AI 전송·공급자 위탁/이전·광고 발송 조건은 실제 계약과 출시 지역 기준으로 확인한다.
- 운영자 화면: 사용자·구독·연결·사용량·비용·실패 작업·흐름/템플릿 버전·지원 이력.
- 장애는 입력/연결/쿼터/공급자/내부 오류로 구분하고 요청 ID와 다음 행동을 제시한다.

16-1. 회원관리와 드래그앤드롭 권한관리
- 관리자 회원 목록/검색/필터/페이지/상세와 허용 기본정보 수정·정지/해제·등급 지정/해제·탈퇴/삭제 절차를 구현하라. EMAIL/SNS 별도 계정, 상품과 유효 등급, 워크스페이스, 상태/이력을 표시하되 암호/토큰을 노출하지 마라.
- 권한관리는 등급별 배정과 기능 항목 관리로 나누라. 등급→업무 그룹 선택→그룹/세부 항목 드래그→상세 조정→변경/의존성 확인→권한 변경 적용 순서로 구현하라. 드래그 중에는 초안만 변경하고 취소 가능해야 한다. 버튼/체크박스/키보드 대체를 제공하라.
- 부모는 전체/일부/미허용 표시용 그룹이다. 전체 드래그는 현재 구현·배정 가능한 자식의 명시 코드 집합을 선택한다. 자식을 개별 해제할 수 있고 미래 신규 권한은 일반 등급에 기본 미허용이다. 배정 삭제와 기능 정의 삭제, 표시 순서와 권한 변경을 구분하라.
- 기획안 14.6의 엑셀 권한을 실제 코드/API에 연결하라. 오버뷰·목록·상세·직접/채팅/사진 생성·이름 수정·행 추가/수정/삭제·구조·수식 직접/AI·추가/리셋 import·빈 양식/데이터 export·분석 조회/관리·양식 관리·보관/삭제·복구를 분리하라. 미열거 행동도 광범위 허용에 숨기지 말고 P0 전체 매핑에 포함하라.
- excel.list.read만 있으면 자기 목록의 승인 메타데이터만 반환하라. 상세 셀/원본/파일 URL을 응답에 숨겨 보내지 마라. 상세 클릭은 제한 이유를 표시하고 오버뷰/생성/편집/분석/출력 API도 차단하라.
- 워드/한글/PPT를 각각 독립 권한으로, 프로그램·CRM·일정·연결·발송도 기획안 14.7의 행동별로 분해하라. 예: 일정 조회만 가진 계정은 드래그 수정 불가, 프로그램 빌드 권한은 운영 활성화와 별도, 채널 연결은 발송과 별도.
- 의존 권한 누락은 필요한 항목/이유를 제시하고 함께 추가/취소를 선택하게 하라. 의존 제거도 영향 확인 후 함께 제거/취소하라. 순환·미등록·관리 전용 배정을 차단하고 목록만 허용하는 구성은 성립해야 한다.
- 기능 그룹/항목 CRUD, 검색/상세, 표시명/설명/그룹/순서 수정, 활성/비활성, 영향 확인 삭제를 구현하라. 기존 코드와 연결 행동의 의미는 불변이다. 미연결 항목은 준비 중이며 기능 추가가 실제 코드를 자동 구현한 것으로 표시하지 마라. 등록된 서버 행동 연결키만 사용하고 임의 SQL/URL/실행코드를 관리 입력으로 받지 마라.
- 이름/그룹 이동 시 배정을 보존하고 기능 삭제는 참조/의존/등급을 검사하라. 사용 이력은 보관하며 미사용 미연결 초안은 완전 삭제 가능하다. 고객 업무 데이터는 권한 정의 삭제로 지우지 마라. 관리 필수 기능과 마지막 관리자를 보호하라.
- 적용 전 추가/제거·영향 등급/회원/워크스페이스/예약 작업·사유를 확인하고 원자 정책 버전으로 저장하라. 해당 등급의 기존 사용자에게도 적용하며 결제 금액/주기를 자동 변경하지 마라. 변경 이력과 이전 정책의 새 버전 복원을 제공하라.
- 다음 요청부터 최신 정책을 검사하라. 오래된 로그인 권한/캐시를 신뢰하지 말고 정책 변경과 DB 확정의 경합을 제어하라. 화면·SSE/WebSocket·파일/다운로드·긴 작업 시작/확정/외부 실행에서 다시 검사하라. 이미 발송/다운로드된 결과를 철회했다고 표시하지 마라.
- AI·범용 apply·일괄/복제/복원은 실제 변경 행동 전체의 권한을 검사하라. 하나의 API 허용으로 열 삭제·수식·다운로드까지 우회시키지 마라. ‘이 등급으로 보기’는 시험 미리보기이고 실제 일반 계정 API 검수를 별도 수행하라.

17. 개발 단계와 실제 완료 기준

P0: 기존 설계+일곱 기능 생성/상세/저장 계약, 수식/리셋 복구, 문서 편집/AI/출력 엔진 검증, 앱 버전 다운로드 패키지 구조·실행 검증, 결정 목록.
P1: Spring MVC/Thymeleaf 공통 레이아웃·fragment·JS 요청/편집 상태 모듈+기존 인증/저장 기반+로컬·서버 공통 admin/12345 최초 초기화와 PasswordEncoder 해시 저장·관리자로그인/리다이렉트·회원관리·기능 카탈로그 CRUD·드래그앤드롭 권한 배정/정책 이력/서버 평가기+사업 범위·대시보드 셸·빈 상태·실시간·탐색 복구. 미구현 업무는 준비 중 카탈로그로 표시하고 사용 가능 배정을 금지.
P2: 신규 작업의 사진/대화/직접/Excel 준비→편집→저장→원본 테이블 데이터 센터. 저장 작업은 목록에서 데이터 센터로 직접 진입한다. 조회·계산 열·다중 보고서·다운로드를 데이터 위에 얹고 여러 보기를 재사용한다. 고급 호환/위젯 배치 등은 구현·검증 여부를 따로 기록한다.
P3: 다중 CRM 오버뷰/목록/상세·사업 분리·거래처 연결·구조/고객/보기 편집·사진/질문/직접 생성·분석·일정 상세/반복/예약 영향.
P4: Word/PPT/HWP 사진/채팅/직접 생성, 직접/AI 상세 편집과 글/표/도형 삽입, 문서 버전/출력, 리소스/레이아웃·연결 보고서. HWP 미확보는 미완료.
P5: 고객별 Gmail/Cafe24/SOLAPI·자동화, PG 정기결제·사용량·해지/실패/대사.
P6: 부품 목록/추가/수정/삭제, 직접/AI 앱 구성, V1/V2 불변 저장·빌드·버전별 실행 ZIP·새 환경 실행·활성화/데이터 호환·복구.
P7: 대표 고객 사용성, 실제 파일 열기, 보안/성능/백업 복구, 출시 검수.

- 각 단계마다 실제 입력→서버 처리→DB 저장→재조회→수정→산출물까지 이어져야 한다.
- 외부 설정이 없으면 연동 대기로 표시하고 가짜 성공/임시 로그인/가짜 AI로 대체하지 않는다.
- 테스트 더블은 자동 테스트 전용이며 운영 모드에서 사용할 수 없어야 한다.
- 서비스 운영·계정 등록 준비는 P0부터 병행하지만 실제 외부 발송/청구는 요청된 대상과 범위에서만 수행한다.
- 아직 구현하지 않은 후속 기능은 완료로 표시하거나 유료 사용 가능으로 노출하지 않는다.

v1.2 UX는 새 기능 단계가 아니라 각 단계의 완료 조건이다. P0은 질문/분기·요약·내 양식·선택 속성·저장/취소 명세, P1은 가입/공통 흐름, P2는 세 생성 경로·직접 편집 적용·수식·입출력·분석 보기/재사용, P3은 CRM 조건/입력 폼·일정, P4는 포맷별 정밀 편집, P5는 상황별 연결 안내, P6는 질문형 앱 구성, P7은 실제 고객의 최초/재사용 과제 검증을 포함한다. 새 기능 수보다 완료율·오류·반복 시간 감소를 평가한다.

18. 필수 검수 묶음

- 동일 이메일의 서로 다른 가입 방식이 분리되는가.
- SNS 최초 로그인·가입 중복·필수 정보 누락·동의 취소·동시 콜백이 올바른가.
- 5분 만료·재발송·오입력·재사용이 차단되는가.
- 아이디 찾기는 EMAIL만 SMS 안내하고, 비밀번호 변경 후 자동 로그인하지 않는가.
- A 사용자가 B의 객체/파일/작업/AI 자료에 접근할 수 없는가.
- 무료 팝업의 7일 숨김이 서버 기준·기기 간 유지되는가.
- 전표의 음수·소계·중복·모호한 숫자·앞자리 0이 처리되는가.
- 헤더 이름/순서 변경에도 자료·수식·통계가 유지되는가.
- 파일이 실제 DOCX/XLSX/PPTX/HWP이며 목표 앱에서 열리고 편집되는가.
- 선택 영역 수정·되돌리기가 다른 내용을 손상시키지 않는가.
- 일정에서 등록한 거래처와 CRM이 같은 대상을 사용하는가.
- 반복 일정 취소와 수신거부가 예약 발송에 반영되는가.
- 타임아웃/중복 요청/worker 재시작/웹훅 역순에서 중복 발송·청구·적재를 막는가.
- 동시 AI 작업의 한도 예약과 정산이 정확한가.
- 해지/만료 후 기존 자료가 보존되는가.
- DB와 파일 백업을 실제로 복원할 수 있는가.

18-1. v1.1 추가 인수 검수
- 일곱 기능의 요약/목록/상세가 실제 데이터에 연결되고 탐색 상태가 복원되는가.
- 두 개 이상 엑셀 양식의 데이터/수식/보기/리셋이 독립적인가. 혼합 단위를 합산하지 않는가.
- HTML 그리드와 행 상세 폼의 추가/수정/삭제/붙여넣기·저장/취소·동시 변경 충돌이 올바른가.
- 빈 양식 다운로드는 무변경, 추가 import는 기존 데이터 보존, 리셋은 선택 양식만 원자 교체하는가.
- 리셋의 0건·구버전·실패·중복 요청·동시 수정·복구·이력 참조·자동 발송 영향을 처리하는가.
- 자연어 수식의 단위/대상·예상 결과·저장/취소, 새 행 재계산, 참조 유지·순환/빈값/0나눔, Excel 수식 결과를 검증했는가.
- 실시간 확정 반영·지연/끊김·재접속·중복/역순·권한 범위를 처리하고 초안을 침범하지 않는가.
- 여러 CRM/사업의 필드·고객·위젯·발신 계정이 분리되고 등록 건수/공통 ID 고유 수가 구분되는가.
- 문서 리소스의 사용처/버전과 레이아웃 미리보기/적용/취소가 내용을 보존하는가.

19. 단계별 납품 규칙

- 전체 소스 ZIP을 제공한다. 변경 부분만 요청받지 않은 한 기존 기능이 포함된 실행 가능한 전체 프로젝트를 납품한다.
- 단일 Maven 루트: pom.xml, Maven wrapper, src/main/java, DB migrations, 서버 설정 예제, src/test. Eclipse에서 하나의 Spring Boot 프로젝트로 import한다.
- 화면 원본: src/main/resources/templates의 Thymeleaf 페이지·공통 fragment, static/css·js·vendor의 CSS·업무별 JS·필수 라이브러리, 자원 버전·라이선스·화면 테스트. 별도 React frontend 프로젝트를 만들지 않는다.
- docs: 실행 안내, Ubuntu 운영, 외부 연동, API 계약, 변경사항, 검수 결과, 미완료/외부연동대기 목록.
- scripts: 빌드/실행/백업·복구 보조 파일. 필요성과 실제 실행 환경을 설명한다.
- Windows Eclipse Existing Maven Projects import, JDK17, DB 생성/계정, 서버 설정 입력, Spring Boot 실행, 접속 주소, Thymeleaf·JS/CSS 수정 반영을 정확히 안내한다. 기본 실행에 npm 설치나 프런트엔드 개발 서버를 요구하지 않는다.
- Maven으로 Thymeleaf 템플릿·정적 JS/CSS·필수 라이브러리를 포함한 Spring Boot 실행 JAR를 만들고 Eclipse/JAR 실행을 검수한다. 자원 가공 도구를 선택하면 원본·고정 버전·재현 절차와 결과물을 함께 제공하되 기본 웹 실행은 별도 프런트 서버 없이 가능해야 한다. 외부 문서 엔진 등 별도 서비스 조건은 따로 설명한다.
- 기본 빌드 명령·버전·수행 결과·실행하지 못한 검수를 명시한다. 확인하지 않은 성공을 쓰지 않는다.
- 저장 데이터 마이그레이션은 버전 파일로 제공하고 비파괴 적용을 우선한다. 롤백 불가 변경은 백업·복구 계획을 제공한다.
- 요구사항 ID ↔ 화면/API/DB ↔ 구현 파일 ↔ 테스트 결과의 추적표를 갱신한다.
- TODO·생략·나머지 동일·가짜 성공 응답·동작하지 않는 메뉴를 핵심 완성 기능에 남기지 않는다.
- 실제 시크릿·고객 개인정보·node_modules·불필요한 임시 파일은 ZIP에서 제외한다.

v1.8 추가 확정 — 엑셀 프로젝트 안의 여러 시트
- 하나의 프로젝트 안에 여러 시트를 둔다. 사진 한 장으로 별도 프로젝트를 만들기와 여러 사진을 한 프로젝트의 여러 시트로 만들기를 모두 지원한다.
- 편집의 시트 추가는 직접 입력 / AI·대화 / 엑셀·CSV / 사진 중 선택한다. 이름 변경·순서 이동·복제·삭제와 미저장 입력 보존을 함께 제공한다.
- 다중 시트 XLSX는 전체 시트를 먼저 검사하고 정상 시트만 선택해서 가져온다. 숨김·빈 시트·계산값 없는 수식·Excel 오류·병합 범위·차트 전용·객체만 있는 시트의 이유와 복구 방법을 구분한다.
- 읽을 수 없는 사진은 실제 관찰한 위치와 이유를 설명하고 재촬영·자르기·고해상도 원본·직접 입력으로 이어간다. 추측한 숫자를 확정 데이터로 만들지 않는다.
- AI는 지정 시트만 읽고 제안한다. 여러 사진은 사진별 성공/질문/실패를 보여주고 준비된 시트만 선택 적용한다. 전송 동의·권한·버전·비용 예약을 생략하지 않는다.
- 저장·되돌리기·XLSX 출력·빈 양식 재사용은 모든 시트를 처리한다. 분석 보기는 안정된 시트 ID를 포함한다. 삭제된 시트를 다른 시트로 몰래 대체하지 않는다.
- 원본은 기존 회원/사업/업무/프로젝트 경로에 한 번 저장하고 시트는 원본 ID를 참조한다. 원본 삭제와 저장 셀 삭제는 별개 동작이다.
- 현재 한도는 프로젝트 20시트, 시트별 20열/200행, 사진 AI 요청당 최대 3장/6MB다. 이를 늘릴 때 저장·미리보기·비용·취소·부하 검사까지 함께 확장한다.
- 현재 가져오기는 수식의 저장된 계산값을 사용한다. 임의 Excel 함수·시트 간 수식·차트 객체 복원을 구현했다고 표시하지 않는다.
- 구체적인 현재 계약과 적용/롤백 방법은 docs/V060_ARCHITECTURE.txt 및 docs/V060_APPLY.txt를 따른다. 기존 기획의 나머지 범위를 삭제하거나 완료 처리하지 않는다.


[0.6.1 저장소 정책 추가 — 2026-10-25 사용자 요청 우선]
집 Windows/사무실 Windows/Mac은 서버 DB를 공유하고 원본 바이트는 각 실행 PC에 따로 저장한다.
PC 변경 시 폴더 복사·DB 재바인딩을 요구하지 않는다. 없는 원본은 현재 PC의 없음 상태로 표시하고 프로젝트 편집은 계속 허용한다.
같은 자료 ID로 원본 교체 가능. 교체는 DB의 원본 정보만 공유하며 바이트를 다른 PC에 복제하지 않는다.
로컬 파일 없음 상태를 DB 전체 파일 삭제로 해석하거나 공유 storage_state에 기록하지 않는다.
회원 소유권/사업·업무·작업 분류/경로 안전성/형식·크기 검증/CSRF/낙관적 버전/AI 사용량은 유지한다.
이전 원본 기반의 미적용 AI 제안은 교체 후 적용하지 않는다. 이미 저장된 시트 데이터는 유지한다.
관리자는 모든 회원의 DB 자료 + 현재 실행 PC의 경로를 관리한다. 원격 PC 디스크 자동 관리로 표시하지 않는다.
상세 동작·적용: V061_APPLY.txt, V061_ARCHITECTURE.txt.


v1.9 추가 확정 — 저장 데이터 센터를 중심으로 한 실무 흐름

1. 사진/대화/직접/Excel에서 가공한 통합문서를 저장하면 1차 완료다. 저장된 표 전체를 먼저 보여라.
   보기 하나를 만들도록 설정 폼을 앞세우지 마라. 목록에서도 실제 저장 표 여부로 대시보드 진입을 제공한다.
2. 사용자에게 현재 시트/저장본/조건 일치 수를 보여 주고, 조회 조건·정렬/표시 열·계산 열·보고서·보기 저장·
   다운로드를 선택할 때 그 패널 하나만 펼친다. 버튼 높이/간격을 통일하고 긴 셀렉트와 큰 완료 카드를 줄인다.
3. 같은 열을 여러 번 선택하는 AND 범위 조건, 여러 우선순위 정렬, 여러 X 기준의 조합과 여러 Y 집계를 지원한다.
   조건은 원본에 먼저 적용하고 집계한다. 보고서 표와 파일은 같은 결과를 사용하며 페이지 때문에 행을 누락하지 않는다.
4. 현재 데이터의 실제 열/값을 사용한 거래처 조회·월별 합계·계산 열 예시를 제시한다. 존재하지 않는 값을 지어내지 마라.
   그래프 종류는 데이터 구조에 맞춰 활성화하며 항목 생략 수/숫자 집계 제외 수를 드러낸다.
5. 계산 열은 실제 원본 오른쪽에 추가한다. SUM/IF/SUMIF/VLOOKUP/INDEX-MATCH 등 템플릿과 직접 수식을 제공한다.
   수식/적용 행/결과/오류를 미리보고 저장한다. 추정값으로 오류를 메우지 말고 원본 입력·기존 수식·행 주소를 보존한다.
   대화는 기존 AI의 전송 범위·동의·검토/적용·사용량 정책을 재사용한다. 큰 표 전체 전송을 몰래 하지 않는다.
6. 원본 수정과 보기 수정을 구분한다. 원본의 값·활성 수식은 재계산하며, 저장된 보기는 최신 저장본을 참조한다.
   여러 보기의 복제/덮어쓰기/삭제는 원본 삭제와 별개다. 필드 삭제로 깨진 보기는 임의 열에 연결하지 마라.
7. 현재 보기 전체 결과 XLSX/CSV와 원본 전체 시트·수식 XLSX를 구분한다. 100행 UI 페이지나 그래프 표시 한도로
   파일 내용을 잘라내지 마라. 내려받는 결과의 조건과 원본 버전을 검증한다.
8. 향후 Word/CRM 등도 저장 자료/레코드 자체가 기본 화면이고, 보기·보고서·내보내기가 그 위에 붙는 구조로 재사용한다.
   데이터 타입과 권한은 해당 업무별로 검증한다. 모든 업무를 Excel JSON에 억지로 넣지 마라.
9. 0.9 구현 한도/실행 검증은 V090 문서가 기준이다. 위젯 배치/교차표/그래프 이미지 출력/예약 발송과
   운영 부하/실브라우저 검수는 별도 과제다. 이전 명세와 충돌하면 이 개정의 저장 데이터 우선 흐름을 적용한다.
